# 地獄のICT 工程表

この文書は、企画を本番アプリへ進めるための進捗の正典である。企画・技術判断の正典は [企画書](企画書.md) とし、本書は判断を再定義せず、工程の状態、成果物、完了条件を管理する。

初めて読むときは「現在地」「次に着手する工程」「直近アクション」を読む。各工程の詳細は、担当作業を始めるときに参照する。

## P1Aで、実装と検証を再現できる開発ハーネスを作る

**状態:** 完了。

**目的:** 本番機能を追加する前に、React/Vite、Cloudflare Workers、Durable Objectsを同じリポジトリで安全に開発・テスト・CI実行できる基盤を整える。完了の基準は、新規cloneした環境で依存関係を導入し、開発環境を起動し、ローカルとCIで同じ検証を通せることとする。

**成果物:**

- pnpm workspaceと、フロントエンド・Worker・共有ドメインコードを置く構成。
- React/Viteのフロントエンド、WorkersとDurable Objectsの最小起動構成、Cloudflareローカル開発設定。
- strict TypeScript、lint、format、テストランナー、CI設定。
- ドメイン、UI、外部サービスadapterの依存方向を示すルールと最小の実装例。
- 外部入力を実行時に検証するruntime schemaと、schemaから推論した型を使う境界。
- Clock、乱数、ID生成、OpenAI、Storageを差し替えるためのinterfaceとFake実装。
- `pnpm verify` と `pnpm verify:full`、およびそれらを実行するCI。

**完了条件:**

1. pnpm workspaceとして依存関係を一括導入でき、React/ViteとWorkers/DOのローカル開発を起動できる。
2. TypeScriptはstrict設定で動作し、外部入力はruntime schemaを通してドメインへ渡る。`any`や根拠のない型アサーションを導入しない。
3. UI、ゲームルール、外部サービスadapterの依存方向が一方向で、ゲームルールと時間処理を副作用のない関数としてテストできる。
4. Cloudflareのローカル環境でWorkerとDurable Objectの最小統合テストを実行できる。
5. 時刻、乱数、ID生成、OpenAI、StorageをFakeに差し替え、失敗・タイムアウト・重複イベントをテストから再現できる。
6. `pnpm verify` がformat、lint、型検査、React/ViteとWorkerのbuild、ドメインテスト、教材整合テスト、Worker統合テスト、主要E2Eを実行する。
7. `pnpm verify:full` が全E2E、全体Mutation Testing、重複検査、依存関係監査を実行する。重い検査は監査レーンとして分ける。
8. CIがローカルと同じpackage scriptsを実行し、新規clone相当の環境で `pnpm verify` が成功する。

**依存関係:** H0。P0の実測結果のうち、ゲーム固有の閾値や時間は後から反映する。

## P1CではAI利用と保存の安全境界を通す

**状態:** 進行中。チャット骨格（複数スレッド、OpenAI adapter、冪等な送受信）と送信前PIIゲートが完了。利用制限、D1ログ、障害耐性の分類は未着手。Stage 4のインシデント発火・罰ゲームは、`teamState`にインシデント/罰の状態機械が無いためStage 4実装（P3。P2はStage 1・2・3が対象）へ送る。

**目的:** アプリ内AIチャットをWorkers経由で提供し、会話ログと複数スレッドを保存しながら、PIIを外部送信前に確実に止める。

**成果物:** OpenAI proxy adapter、会話スレッドとログ、チーム別利用制限の境界、PII検知・インシデント発火、保存先のD1の接続。KV・R2はP1Cの対象外とし、教材配布と接続する時期（P2以降）にあらためて判断する。

**完了条件:** チームごとに複数スレッドを扱え、AIキーはクライアントへ出ない。PII検知時はOpenAI呼び出し回数が0で、ログ・状態・画面が定義どおりに遷移する。保存失敗、レート制限、OpenAI障害をFakeと統合テストで扱える。

**実装記録:** [P1C AI・保存基盤](p1c-ai-and-storage.md) に、チャットの状態・冪等性・OpenAI adapterの境界を記録する（実装の進行に合わせて追記する）。

**依存関係:** P1A、P1B。ゲーム固有の検知パターンはP0で確認した教材と企画書に従う。

## P2ではStage 1・2・3を実装し、研修の核を実プレイする

**状態:** 未着手。

**目的:** AIのない地獄からAIを獲得するStage 1、AIの本領で成功体験を作るStage 2、その信頼を裏切って罠→罰→アプリ内マニュアル照合で復旧するStage 3という一続きの3段構成を実装し、ゲームの学習構造を検証する。Stage 3の罠はStage 2で積んだ「AIすごい」という信頼を裏切ることで刺さる設計であり、Stage 2を欠いた実プレイでは罠の教育効果そのものを検証できないため、Stage 2をP2に含める。

**成果物:** Stage 1・2・3の画面、ルールベース判定、実プレイ記録。Stage 2は7列固定の編集可能グリッド（汚い生データ23行）、締切5分の非ロック超過処理と追加10行の着弾、AIチャットパネルの遅延出現、解錠時の流行曲線。Stage 3は汚染教材とシステムプロンプト注入、罰ゲーム、アプリ内マニュアルビューア。

**完了条件:** Stage 2は締切超過で提出をロックせず、追加分の着弾が1回に留まり、手作業ルートとAI貼り付けが同じグリッドへ合流する。Stage 3の罠はモデルの気まぐれに依存せず発動し、復旧はアプリ内ビューアの正典照合だけで完結する。禁止状態遷移、判定漏れ、罰の重複適用をテストで防ぎ、PC1台の実プレイで確認する。

**依存関係:** P0、P1B、P1C。

3. P2はStage 1・2・3を対象とする。企画書のStage 3をノロウイルス版へ揃える改訂が完了しているため、着手時は改訂後の企画書・シナリオを参照する。
4. 重要な選択肢が残る場合は、実装を始める前に選択肢と影響を確認する。

## 状態と更新のルールを守る

- 状態は「未着手」「進行中」「完了」「保留」のいずれかで記す。完了条件を満たしていない工程を完了にしない。
- 進捗率、根拠のない日付、工数は記載しない。実測値が確定した場合は、根拠と対象条件を添えて企画書へ反映する。
- 企画・技術判断を変えるときは、先に [企画書](企画書.md) を更新し、本書には工程への影響だけを反映する。
- 各工程の成果物または完了条件が変わったときは、この工程表を同じPull Requestで更新する。
- 実測、テスト、パイロットで判明した未解決事項は、該当工程の下に追記するか、作業を開始するPull Requestへ記録する。
