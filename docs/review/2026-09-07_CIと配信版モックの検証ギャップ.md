## 結論

GitHub Actions の本番デプロイは、基準SHAで成功している。デプロイworkflowには `pnpm verify` ジョブがあり、検証を通過してから `build:testplay` と本番デプロイを実行するため、GitHub上のCIそのものが止まっているわけではない（[.github/workflows/deploy.yml](../../.github/workflows/deploy.yml#L21-L63)）。

一方で、既存のPlaywright E2Eは `apps/web` のVite開発サーバーを対象にしており、`build:testplay` が生成する配信物を直接開いていない（[playwright.config.ts](../../playwright.config.ts#L14-L35)、[scripts/build-testplay.sh](../../scripts/build-testplay.sh#L1-L19)）。そのため、モックを変更したときに「配信対象のHTML・静的資産として問題なく動く」ことは、現在のE2Eだけでは固定されない。次の作業は、生成後の `apps/worker/public/` を配信する検証を追加することを優先する。

## 調査の対象外

UI改修フェーズではモックが正典である。このため、モックと `docs/企画書.md`、`docs/scenario/`、`docs/ui/`、`docs/character/`、`docs/materials/` の内容の一致は確認していない。これらの文書との齟齬は、本記録の指摘対象ではない。

また、`docs/testplay/2026-08-23_進行台本.md` は実施記録であり、現時点の実装との差異も調査対象外とした。

## 確認した事実

### GitHub Actions は基準SHAで成功している

- 本番デプロイの実行 [#34053499845](https://github.com/yukihiroyamaguchi569/hell-ict/actions/runs/34053499845) は成功した。開始時刻は 2026-09-06 19:00:36 UTC、対象SHAは `b7d842be143d3c324a09ffc0501709c6c3d7f334` である。
- このSHAは [PR #134](https://github.com/yukihiroyamaguchi569/hell-ict/pull/134)（`refactor: ステージ内部名と URL ハッシュを表示番号に揃える（#118）`）のマージコミットで、2026-09-06 19:00:33 UTCにmainへマージされた。
- デプロイworkflowは、まず `pnpm verify` を実行し、その成功を `needs: verify` で要求している（[.github/workflows/deploy.yml](../../.github/workflows/deploy.yml#L21-L52)）。
- 独立した `verify.yml` のmain向け直近成功runは [#34005553453](https://github.com/yukihiroyamaguchi569/hell-ict/actions/runs/34005553453) である。このworkflowはPR向けであり、mainへのpushはデプロイworkflow内の同等検証に委ねている（[.github/workflows/verify.yml](../../.github/workflows/verify.yml#L3-L11)）。

### E2Eと実際の配信物の対象が異なる

PlaywrightはOpenAIスタブ、Worker、`@hell-ict/web` の開発サーバーを起動する。WebサーバーのURLは `http://127.0.0.1:4173` であり、生成済みモックの配信先ではない（[playwright.config.ts](../../playwright.config.ts#L14-L35)）。実際のE2Eも `/` へアクセスし、アプリの入室・復元・チャットなどを検証している（[e2e/harness.spec.ts](../../e2e/harness.spec.ts#L5-L14)、[e2e/chat.spec.ts](../../e2e/chat.spec.ts#L5-L22)）。

一方、本番デプロイは `pnpm build:testplay` を実行する。このスクリプトは `docs/ui/mock/index.html` と本番画像を `apps/worker/public/` にコピーし、WorkerのAssetsとして配信する（[package.json](../../package.json#L10-L13)、[scripts/build-testplay.sh](../../scripts/build-testplay.sh#L1-L19)、[.github/workflows/deploy.yml](../../.github/workflows/deploy.yml#L60-L63)）。従って、両者は別の成果物を見ている。

### path filterは修正候補である

PR用のverify workflowは `paths-ignore` に `docs/**` と `!docs/materials/**` を並べている（[.github/workflows/verify.yml](../../.github/workflows/verify.yml#L3-L11)）。GitHub公式の[workflow構文](https://docs.github.com/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore)では、包含と除外を組み合わせる場合は `paths` で順序付きパターンを使う。`paths-ignore` 内の否定パターンに、教材だけを再包含する意図を任せるのは仕様上の根拠が弱い。

教材を変更したPRでも確実に検証を起動する必要があるなら、`paths-ignore` から `paths` へ移し、`docs/**` を除外した後に `!docs/materials/**` を再包含する形を、変更パスを分けたworkflowテストまたは実PRで確かめる。

## 訂正と限界

- ローカルで `.claude/worktrees/` や `tasks/` をlint対象が拾う問題は、GitHub Actionsのクリーンcheckoutには通常存在しない。CI障害ではなく、ローカル開発体験の改善候補として扱う。
- `wrangler types --check` の生成型差分は、調査開始時に最新mainより古い `fix/s35-director-grace` 上で観測した。基準SHAのデプロイと検証が成功しているため、現行mainの問題としては扱わない。
- 本調査はworkflow定義、E2E設定、配信生成スクリプト、GitHub Actionsのrun結果を確認した。実際の本番ブラウザで全モック画面を操作する検証は行っていないため、配信版E2Eを追加した後に、そのテスト範囲を改めて決める必要がある。

## 次作業で確認する改善候補

### 1. 配信版モックのE2Eを追加する

`pnpm build:testplay` の後、`apps/worker/public/` を静的サーバーまたはWorkerのAssets経由で開くPlaywrightプロジェクトを追加する。少なくとも次を確認する。

- HTMLの読み込み時に `pageerror` が発生しない。
- 配信版では開発用UIが露出しない。
- 入室、再読み込み後の復元、主要ステージ遷移、PII送信ブロックが動く。
- 演出中の連打や画面遷移で、古い非同期処理が現在画面を上書きしない。

既存E2Eを置き換えるのではなく、`apps/web` の統合確認と配信版モックの確認を別プロジェクトとして並べる。これにより、どちらの成果物で壊れたかを切り分けられる。

### 2. `docs/materials/**` のCI起動条件を明確化する

workflowを `paths` の順序付きパターンへ変更する。変更後は、次の三つを確認する。

- `docs/materials/**` のみの変更でverifyが起動する。
- その他の `docs/**` のみの変更ではverifyをスキップする。
- コードと教材を同時に変更した場合にもverifyが起動する。

### 3. 進行を止めない失敗を観測できるようにする

活動ログの非同期書き込みは、ゲームの進行を止めないために失敗を握り潰している（[apps/worker/src/activity-log.ts](../../apps/worker/src/activity-log.ts#L179-L183)）。この判断は維持しつつ、構造化ログまたは欠損件数の計測を加え、研修後の分析ログが欠けたときに検知できるようにする。

デプロイ後のsmoke testは、現在の `/api/health` と効果音ファイルの確認に加え（[.github/workflows/deploy.yml](../../.github/workflows/deploy.yml#L79-L112)）、モックHTMLの200応答・期待する固有マーカー・主要静的画像・D1を読むsummary APIを対象にできる。ネットワーク障害とアプリ異常を区別できるよう、失敗時にはURLと応答概要を出力する。

### 4. モック内の遅延処理に失効境界を設ける

モックは `later()` で登録したタイマーを `clearLater()` で解除できる。一方、Promiseとして作る `wait()` は画面遷移後も完了しうる（[docs/ui/mock/index.html](../../docs/ui/mock/index.html#L1987-L1998)）。画面世代番号または `AbortSignal` を導入して、前の画面に属する遅延処理がUIを更新できない境界を設ける。

## 推奨順序と再現手順

1. `docs/materials/**` のpath filterを `paths` ベースへ直し、PRの変更パスごとにActions起動を確認する。
2. `build:testplay` 済みの成果物を開くPlaywrightプロジェクトを追加し、まずHTML読み込み、入室、復元、PIIブロックを固定する。
3. デプロイ後smoke testと活動ログの観測を追加する。
4. モックの画面遷移・演出を対象に、遅延処理の失効境界を実装し、連打・遷移の回帰テストを加える。

ローカルでの最小再現は、`pnpm build:testplay` 実行後に `apps/worker/public/index.html` を静的サーバーで開く。この手順をPlaywrightの `webServer` に組み込み、`apps/web` を開く既存プロジェクトとは別に実行する。CIの起動条件は、変更パスをそれぞれ1ファイルだけにした小さなPRで、Actions画面のworkflow開始有無を確認する。
