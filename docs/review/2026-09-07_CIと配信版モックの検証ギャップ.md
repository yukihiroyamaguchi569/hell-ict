## 訂正

初回記録で「`docs/materials/**` の変更ではPR向けverifyが起動しない可能性がある」とした点を撤回する。教材を含む [PR #111](https://github.com/yukihiroyamaguchi569/hell-ict/pull/111) では、verify run [#34010166850](https://github.com/yukihiroyamaguchi569/hell-ict/actions/runs/34010166850) が成功している。現在の `paths-ignore` 設定は教材の再包含を実際に満たしている。`paths` の順序付きパターンへの移行は、GitHub公式の推奨に寄せる任意の整理であり、障害対応ではない。

最優先で解消すべきなのは、配信対象の [`docs/ui/mock/index.html`](../ui/mock/index.html) が `docs/**` に含まれるため、モックだけを変更したPRではverifyが起動しないことと、起動した既存E2Eが配信版モックを開かないことの組み合わせである。[PR #131](https://github.com/yukihiroyamaguchi569/hell-ict/pull/131) と [PR #132](https://github.com/yukihiroyamaguchi569/hell-ict/pull/132) には `pnpm verify` の実行がない。モック変更をPRで再包含し、`build:testplay` の成果物を検証するE2Eを同時に追加する。

## 結論

GitHub Actionsの本番デプロイは、基準SHAで成功している。デプロイworkflowは `pnpm verify` の成功後に `build:testplay` と本番デプロイを実行するため、CI全体が停止しているわけではない（[.github/workflows/deploy.yml](../../.github/workflows/deploy.yml#L21-L63)）。

ただし、PR向けverifyは `docs/**` を除外しており、正典であり配信元でもある `docs/ui/mock/index.html` の単独変更を検証しない。さらに既存Playwright E2Eは `apps/web` のVite開発サーバーを対象にしていて、`build:testplay` の配信物を直接開かない（[playwright.config.ts](../../playwright.config.ts#L14-L35)、[scripts/build-testplay.sh](../../scripts/build-testplay.sh#L1-L19)）。次の変更では、この二つをセットで解消する。

## 確認した事実

### GitHub Actionsは基準SHAで成功している

- 本番デプロイの実行 [#34053499845](https://github.com/yukihiroyamaguchi569/hell-ict/actions/runs/34053499845) は成功した。対象SHAは `b7d842be143d3c324a09ffc0501709c6c3d7f334` である。
- このSHAは [PR #134](https://github.com/yukihiroyamaguchi569/hell-ict/pull/134) のマージコミットである。デプロイworkflowは `pnpm verify` の成功を `needs: verify` で要求する（[.github/workflows/deploy.yml](../../.github/workflows/deploy.yml#L21-L52)）。
- [#34005553453](https://github.com/yukihiroyamaguchi569/hell-ict/actions/runs/34005553453) はPR向けrunではなく、mainへのpushで起動したrunである。PR向けverifyの成功例は [#34053198914](https://github.com/yukihiroyamaguchi569/hell-ict/actions/runs/34053198914) である。

### モックのPR変更はverify対象から外れる

PR用verify workflowは `paths-ignore` で `docs/**` を除外する（[.github/workflows/verify.yml](../../.github/workflows/verify.yml#L3-L11)）。そのため、`docs/ui/mock/index.html` だけを変更するPRはverify対象外となる。実際にモック中心のPR #131と#132には `pnpm verify` がない。

一方、`docs/materials/**` の変更は同設定で再包含されている。PR #111と成功run #34010166850がその実証である。`paths` への移行は、設定の意図を読みやすくする任意の整理として扱う。

### E2Eと実際の配信物の対象が異なる

PlaywrightはOpenAIスタブ、Worker、`@hell-ict/web` の開発サーバーを起動し、`http://127.0.0.1:4173` を開く（[playwright.config.ts](../../playwright.config.ts#L14-L35)）。実際のE2Eは入室、復元、チャットを検証するが、配信版モックではない（[e2e/harness.spec.ts](../../e2e/harness.spec.ts#L5-L14)、[e2e/chat.spec.ts](../../e2e/chat.spec.ts#L5-L22)）。

本番デプロイでは `pnpm build:testplay` が `docs/ui/mock/index.html` と画像を `apps/worker/public/` にコピーし、WorkerのAssetsとして配信する（[package.json](../../package.json#L10-L13)、[scripts/build-testplay.sh](../../scripts/build-testplay.sh#L1-L19)、[.github/workflows/deploy.yml](../../.github/workflows/deploy.yml#L60-L63)）。したがって、既存E2Eと本番配信物は別の成果物を見ている。

## 配信版E2Eの構成

静的サーバーで配信版HTMLを開く検証は、HTMLの読み込み、`pageerror` の不在、開発用UIの非表示、主要静的資産の取得に限定する。これは軽量なsmoke testとして有効である。

一方、入室、再読み込み後の復元、PII送信ブロックは同一オリジンのAPIを使う。これらは静的サーバーだけでは検証できない。WorkerのAssets経由でモックとAPIを同一オリジン配信するか、同一オリジンのAPI proxyを用意したPlaywrightプロジェクトで検証する。既存の `apps/web` 統合E2Eは置き換えず、別プロジェクトとして並べる。

## 訂正と限界

- ローカルで `.claude/worktrees/` や `tasks/` をlint対象が拾う問題は、GitHub Actionsのクリーンcheckoutには通常存在しない。現行CIの問題ではなく、ローカル開発体験の改善候補である。
- `wrangler types --check` の生成型差分は、調査開始時に最新mainより古いブランチで観測した。基準SHAのデプロイと検証が成功しているため、現行CIの問題としては扱わない。
- 本調査はworkflow定義、E2E設定、配信生成スクリプト、GitHub Actionsのrun結果を確認した。実際の本番ブラウザで全モック画面を操作する検証は行っていない。配信版E2Eを追加する際に、画面ごとの対象範囲を定める必要がある。

## 次作業で確認する改善候補

### 1. モック変更でverifyを起動し、配信版E2Eを追加する

`docs/ui/mock/index.html` の変更をPR向けverifyの対象へ再包含する。同じ変更で `pnpm build:testplay` 後の `apps/worker/public/` を対象に、二段の検証を追加する。

- 静的smoke testでは、HTML、主要資産、`pageerror`、開発用UIの非表示を確認する。
- 同一オリジンのWorker AssetsまたはAPI proxyを使うE2Eでは、入室、復元、主要ステージ遷移、PII送信ブロックを確認する。
- 演出中の連打や画面遷移で、古い非同期処理が現在画面を上書きしないことを確認する。

### 2. 進行を止めない失敗を観測できるようにする

活動ログの非同期書き込みは、ゲーム進行を止めないために失敗を握り潰している（[apps/worker/src/activity-log.ts](../../apps/worker/src/activity-log.ts#L182-L182)）。この判断は維持しつつ、構造化ログまたは欠損件数の計測を加え、研修後の分析ログの欠落を検知できるようにする。

デプロイ後のsmoke testは、現在の `/api/health` と効果音ファイルの確認に加え（[.github/workflows/deploy.yml](../../.github/workflows/deploy.yml#L79-L112)）、モックHTMLの200応答、期待する固有マーカー、主要静的画像、D1を読むsummary APIを対象にできる。失敗時にはURLと応答概要を出力する。

### 3. モック内の遅延処理に失効境界を設ける

モックは `later()` で登録したタイマーを `clearLater()` で解除できる。一方、Promiseとして作る `wait()` は画面遷移後も完了しうる（[docs/ui/mock/index.html](../../docs/ui/mock/index.html#L1989-L1998)）。画面世代番号または `AbortSignal` を導入して、前の画面に属する遅延処理がUIを更新できない境界を設ける。

## 推奨順序と再現手順

1. `docs/ui/mock/index.html` の変更でPR向けverifyが起動するよう設定し、モックだけを変更したPRでActions起動を確認する。
2. `build:testplay` の成果物に静的smoke testを追加し、HTML、主要資産、`pageerror`、開発用UIの非表示を固定する。
3. Worker Assetsまたは同一オリジンAPI proxyで配信版E2Eを追加し、入室、復元、主要ステージ遷移、PII送信ブロックを固定する。
4. デプロイ後smoke testと活動ログの観測を追加する。
5. モックの画面遷移・演出に遅延処理の失効境界を実装し、連打・遷移の回帰テストを加える。

ローカルでは、`pnpm build:testplay` の後に `apps/worker/public/index.html` を静的サーバーで開き、静的smoke testを実行できる。APIを含むE2Eは、このサーバーではなくWorker Assetsまたは同一オリジンAPI proxyを経由させる。CIの起動条件は、モックだけを変更した小さなPRでActionsのworkflow開始有無を確認する。
