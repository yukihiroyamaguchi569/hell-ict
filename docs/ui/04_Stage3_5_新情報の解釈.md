## 狙い

**長い論文をAIで要約し、その一語が院内の動きを変えるところまでを、6分で見せる。**

画面の役割は、論文・AIの要約・院長への報告文を同時に見せること。参加者が「眼痛を探せ」という問題を解くのではなく、院長から頼まれた要約を真面目に作った結果、次の感染対策に使える情報を見つける構造にする。

---

## 0. 開始：院長のタスク付与と転送メール

Stage 3の解錠後、`data-mode="crisis"`を保ったままヘッダーを `原因不明の発熱 14` に切り替える。続けて院長が肖像付きのタスク付与オーバーレイ（`#ov-s35-director`。Stage 3の急変通知`#ov-s3notice`と同じ器）で要約を命じる。全画面ブリーフィングや赤帯は使わない。

```
📞 内線 ── 院長
┌──────────────────────────────────────────────┐
│ ┌────┐  14名も発熱者が増えているじゃないか！！   │
│ │肖像│  周辺国・東陵国で、原因不明の発熱クラス   │
│ │院長│  ターが出ているそうだ。速報論文が届いて   │
│ └────┘  いる。                                │
│         英語だ。要約して、私に上げなさい。       │
│         以上だ。期待している。                  │
│                            [ 了解しました ]    │
└──────────────────────────────────────────────┘
```

肖像が話者を示すので、本文へ話者表記`〔〕`は付けない（`#ov-s3notice`・`#ov-s4call`と同じ流儀）。1行目はヘッダーの発熱表示が9→14へ動いた直後の第一声で、2026-08-22にユーザー指示で追加した。

閉じると通常画面へ戻り、受信トレイに転送メールが一通ある。

```
件名: 周辺国の速報論文
差出人: 院長室

院長よりお話のあった、東陵国の速報論文を添付いたします。
📎 東陵国感染症監視局　クラスター速報No.18.pdf
```

要約の依頼はオーバーレイで院長本人が告げるので、メール本文へ重複させない。差出人は「院長室」（実務は秘書等が送る想定、実在名は出さない）。添付を開くと教材ビューアに英語の速報論文が出る。`[コピー]`を置き、AIチャットへ貼り付ける動線を塞がない。メール本文には、眼痛、発熱前、夜勤者、感染対策といった解法の手がかりを入れない。

## 1. 画面全体

Stage 2以降の3ペインを踏襲する。左に転送メールと論文、中央に報告欄、右にAIチャットを置く。

```
┌──────────────────────────────────────────────────────────────────────┐
│ 🏥 聖クロノス総合病院 ICT │ 原因不明の発熱 14              │ 47:16 │ B班 │
├────────────────┬────────────────────────────┬────────────────────────┤
│ 受信トレイ 1     │ ▸ 新情報の解釈                │ AIチャット              │
│ ────────────  │ ────────────────────────  │                        │
│ ● 院長室         │ 速報論文をAIで要約し、          │ 〔あなた〕論文を要約…   │
│   周辺国の速報論文 │ 院長へ報告してください。         │ 〔AI〕…                 │
│  📎 速報論文.pdf │                              │                        │
│                │ ┌─ 院長への要約 ───────────┐ │                        │
│                │ │                              │ │                        │
│                │ └──────────────────────────┘ │ [                    ] │
│                │          [ 院長へ報告 ]         │ [送信]                 │
├────────────────┴────────────────────────────┴────────────────────────┤
│ Prologue ─ S1 ──── S2 ──── S3 ──── ◆ ──── S4 ──── S5 ─── Final     │
└──────────────────────────────────────────────────────────────────────┘
```

中央の依頼文は「速報論文をAIで要約し、院長へ報告してください」だけにする。抽出すべき症状や、その後の対応をUIで教えない。

## 2. 要約報告後の一往復

要約が条件を満たすと、院内連絡先ウィンドウが一度だけ前面に出る。院長は常駐せず、この画面を閉じたら戻らない。

```
〔院長〕要約は読んだ。
〔院長〕うちの発熱患者もこれかもしれないな。
〔院長〕それで、これからどうする？

[                                                    ]
                                      [ 送信する ]
```

自由記述を1ターンだけ受け付ける。回答に応じて選択肢やカードを出さない。参加者が、論文から得た情報を「夜勤者に眼痛がないか確認する」という行動へ自分たちで翻訳する余地を保つためである。

具体性が足りない場合は、同じウィンドウ内で一度だけ「誰に、何を確認したいのかを教えて」と返す。眼痛という正解語は示さない。

**確認する相手が患者へ向いている提案には、専用の差し戻しを返す**（2026-08-22追加）。「入院患者で眼痛のある患者を探す」のように眼症状は掴めているのに相手が既に発熱している側を向いている場合、汎用の差し戻しは「対象は書いたのに」と読めて的外れになる。不正解の扱いは変えないまま、「調べさせた。患者は皆すでに発熱していて、眼痛を訴える者はいなかった。……論文が言っているのは、熱が出る前の話だ。先回りできる相手は誰だ」と方向だけを指す。**提案された確認は院長が実際にやらせて空振りに終わった、という事実を先に置く**（2026-08-22ユーザー指示で追記）——「まだ調べていないから駄目」ではなく「調べたが、そこには居なかった」なので、探す先を変える理由になる。ここでも正解語（夜勤者）は示さない。

## 3. クリア画面：接点が消える小さな報酬

条件を満たす行動提案を送ると、入力欄と`[送信する]`を閉じ、同じウィンドウ内へ院長の結果報告を表示する。

```
〔院長〕分かった。夜勤者を確認させる。
〔院長〕……発熱はないが、眼痛を訴える応援看護師が一人いた。配置はこちらで変える。
〔院長〕上出来だ。

                                      [ 確認した（次へ） ]
```

3行は一度に出し、**自動では閉じない**（2026-08-22変更・ユーザー決定。以前は2.2秒後に自動で閉じていたが、実プレイで読み切る前に消えると指摘された）。`[確認した（次へ）]`を押して初めてウィンドウが閉じ、次のクリアカードへ進む。ボタンの流儀はStage 1の結果ウィンドウと同じ（`{ once: true }`＋押下時`disabled`）。

続けて、中央ペインを覆う小さなクリアカードを出す。Stage 3の暗転、Stage 4の警報と見分けるため、背景は落とさず、`--ok`の緑だけを使う。

```
         接点をひとつ、減らした。

   新情報を読み解き、これ以上の拡大を防ぎました。
```

カードの背景には、応援看護師が二病棟をまたぐ予定だった配置線が消え、代替担当へ細い線が引き継がれる簡易図を置く。病原体や感染経路の図解はしない。参加者の働きで減ったのは、確定した感染連鎖ではなく、拡大しうる接点だからである。

## 実装メモ

- ステージ名は画面に **「新情報の解釈」** と表示する。全ステージの名称・番号の見直しは別作業とし、`Stage 3.5`を画面上に固定表示しない。
- 論文ビューア、`[コピー]`、AIチャットはStage 2・3の器を再利用する。新しいAI機能や新しい画面遷移は作らない。
- **実装との差分（2026-08-23テストプレイ向けブランチで確認）**:
  - **要約の依頼主・報告先は院長**（2026-08-22ユーザー修正で幹部から差し替え。理由は
    [../scenario/04_Stage3_5_新情報の解釈.md](../scenario/04_Stage3_5_新情報の解釈.md) §状況）。
    受信トレイの差出人は`院長室`、中央ペインは`院長への要約`／［院長へ報告］、§2・§3の話者は`〔院長〕`。
    実装の定数は `S35_DIRECTOR_LINES`・`MAIL_S35_DIRECTOR`・`S35_SUMMARY_REJECT`・`S35_ACTION_REJECT`・
    `S35_RESULT_LINES`。オーバーレイIDだけは `#ov-s35-kanbu` のまま据え置いてある（話者の差し替えで
    配線は変えていない）ので、ID名から「幹部が話す」と読まないこと。
  - 院長の一往復は、本文が想定していた「院内連絡先（PHS・苅部さん）ウィンドウ」ではなく、**専用の
    一回きりオーバーレイ（`#ov-s35-kanbu`）**で実装されている。常駐する相談窓口（苅部さん）を
    増やさないという意図は変わらないが、UI部品としては別物——PHSの窓は流用していない。
  - **画面表示のステージ番号は 2026-08-22 に振り直した**（ユーザー決定）：このステージの表示名は
    **Stage 4**、旧 Stage 4「報告」は Stage 5、旧 Stage 5「掲示」は Stage 6。中央ペインのタイトルは
    `Stage 4　新情報の解釈`、Stage 3 クリア時の解錠オーバーレイは「Stage 4 を解錠しました」になる。
    変えたのは表示文字列だけで、内部ID（`view` 名 `s35`・URLハッシュ `#s35`）・定数プレフィックス
    （`S35_`）・関数名・このファイルを含む `docs/` のファイル名は旧番号のまま据え置いている。
    本文（§0〜§3）の番号表記も旧番号のままなので、読むときは上の対応で読み替える。
  - **リーダーボードの停留所は、この振り直しで S4 として独立させた**（帯は
    `Prologue/S1/S2/S3/S4/S5/S6/Final` の8停留所。`STOP_COUNT = 8`）。以前は Stage 3 の停留所を
    共有していたため、`TEAMS[2].pos` はこのステージのクリア時にしか進まなかった。現在は Stage 3
    クリア（＝このステージの解錠）で `pos = 4`、このステージのクリアで `pos = 5` へ進む。
  - Stage 3.5のクリア時のみ、次のシーンへ**実際に遷移する**（`go("s4")`）。他ステージのクリアは
    状態更新のみで留まりシーン遷移を伴わないのと異なる——devbar・URLハッシュ単体起動での配線検証に
    必要なための例外。
  - **クリア後の送りは自動タイマーではなく、二つの［確認した（次へ）］ボタン**
    （2026-08-22変更・ユーザー決定）。院長の結果報告→ボタン→クリアカード→ボタン→解錠、の二段にする。
    以前は結果報告が2.2秒、カードが2.6秒の自動タイマーで送られていたが、どちらも読み切る前に画面が
    変わるという指摘を受け、参加者自身が押して進む形にした。一画面にまとめず二段のまま残すのは、
    院長の言葉（誰が何をしたか）と報酬カード（配置線の図）が別種の情報で、同時に出すと図が読まれずに
    流れるため。ボタンの流儀は
    Stage 1 の結果ウィンドウと同じ（`{ once: true }`＋押下時 `disabled` で連打を止める）。押す前に
    devbar・右端の引き出しで他ステージへ飛んだ場合は、`view` を見て二重遷移しない。
  - Stage 3クリア→Stage 3.5開始は自動遷移する（`stage3UnlockSequence()`が`go("s35")`を呼ぶ）。
- クリア後は通常の解錠演出へ戻し、Stage 4を開ける。ここでタイマーや罰を追加しない。
