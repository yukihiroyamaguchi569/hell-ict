# Stage 4：情報漏洩（UI設計）

**地獄のICT UI設計 / 目安2分・`alarm`初出・💀罠**
親企画書: [../企画書.md](../企画書.md) ｜ シナリオ: [../scenario/05_Stage4_情報漏洩.md](../scenario/05_Stage4_情報漏洩.md) ｜ 器: [00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) ｜ 前段: [04_Stage3.md](04_Stage3.md)

> ⚠️ 参加者に見えるステージ名は **`Stage 4　回答`**。「情報漏洩」は設計ドキュメント上の呼称であって、
> 画面に出すと罠の存在を予告してしまう（[04_Stage3.md](04_Stage3.md) 冒頭 ⚠️ と同じ理由）。
> 実際にやること（家族への返信文を書く）とも一致する呼称にしてある。

---

## 狙い

**Stage 3 が「判断力」の罠だったのに対し、Stage 4 は「反射神経」の罠。**

企画書 §5「何を渡さないかを知識ではなく反射神経にする」。UIの仕事は、参加者が考える前に手を止められる形の
ゲートを送信経路に用意すること。判定に迷う余地を残さない——**あなたの提出が正しいかを問うのではなく、
何を渡したかだけを見る**。

> 📌 UI設計上の絶対条件: **ブロックは提出フォームではなく、送信の手前で起こす。**
> 企画書 §7「実送信の直前で検知する」。ここを提出時の判定に混ぜると、「書いてから直す」機会が生まれてしまい、
> 反射神経を試す設計にならない。

## `alarm` オーバーレイの初出

[00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §9 に定義だけされていたオーバーレイを、Stage 4 が初めて使う。

- `--accent` のフラッシュ＋全画面の赤帯。Stage 1→2 の急変（赤帯）、Stage 3 の `blackout`（暗転）に続く
  3種類目の緊急演出——**画面が壊れたと錯覚するほど強く**出す。反射神経を試すステージなので、
  この一瞬の驚きそのものが学習の一部になる。
- `blackout` との違い: `blackout` は画面を落として1行だけ残す「事実の静けさ」だったが、`alarm` は逆に
  **画面をフラッシュさせる「事故の音」**にする。演出の質を変えることで、Stage 3 と Stage 4 の罠が
  別種のものだと体で分からせる。
- 文言は2行だけ:
  ```
  個人情報インシデント発生
  送信はブロックされました。
  ```
  責める文言も、安心させる文言（「実際には外部へ出ていません」）も置かない。安心材料は Debrief の種明かしに取っておく。

院内状況インジケータは動かさない（14のまま `--accent` 継続。[05_Stage4_情報漏洩.md](../scenario/05_Stage4_情報漏洩.md) §演出・時間）。

## 1. 左ペイン：着弾メールと共有フォルダ

### 着弾メール（2通）

文面は [05_Stage4_情報漏洩.md](../scenario/05_Stage4_情報漏洩.md) §状況が正典。2003年書式（`--font-legacy`）は継続。
差出人はどちらも近藤さんに繋がる——1通目は「患者相談窓口 近藤」、2通目は師長。

- 初期表示は**1通目（患者相談窓口 近藤）を開いた状態**にする（Stage 3 が検査科メールを開いた状態で始まるのと同じ流儀）。
- **師長のメール添付**（`カルテ抜粋_5A_0710.txt`）は Stage 2・3 の添付ビューアと同じ仕組みで開く。
  **`[コピー]` ボタンを置く**——Stage 3 §1 の生命線と同じ思想。塞ぐと罠が発動しなくなる。
  「病院から届くもの」の書式ルール（[00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §8）に従い、白い紙として固定する。
- **回答期限を超過すると、メールではなく近藤さんの着信ポップアップが割り込む。** 詳細は下記
  「回答期限（課題カードの中に1本）」。

### 共有フォルダ：Stage 3 から常設のまま

[04_Stage3.md](04_Stage3.md) §1「Stage 3 以降 常設のまま残る」を回収する。Stage 4 で内容を増やさない——
Stage 4 に固有の教材（カルテ抜粋）はメール添付だけに置き、共有フォルダには足さない。
共有フォルダの役割は「正解の在り処を示す」ことだったが、Stage 4 の正解は資料の中ではなく**判断の型**にあるため、
新しいファイルを共有フォルダに置く必要がない。

## 2. 中央ペイン：課題と1欄の提出フォーム

### 課題カード

```
 渡辺様のご家族への返信文を作成し、提出せよ。
```

Stage 2・3 と同じく1行に留める。必須要素（面会制限／検査の経過／連絡窓口）は**画面に出さない**——
出すとプロンプトにそのまま写せてしまい、家族の問い合わせを読んで自分で言語化する動機が死ぬ。

### 回答期限（課題カードの中に1本）

```
 渡辺様のご家族への返信文を作成し、提出せよ。

 電話でお待ちです              01:47  ▬▬▬▬▬▬▬▬▬▬▭▭
```

[00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) の「目安時間」は Stage 1〜3 まで演出上の
見積もりに留めていたが、**Stage 4 だけ実際のカウントダウンにする**——焦りが罠の発火率に直結するステージ
だから（[05_Stage4_情報漏洩.md](../scenario/05_Stage4_情報漏洩.md) §回答期限）。

| 項目 | 決定 | 理由 |
|---|---|---|
| 配置 | Stage 2 の締切と同じ「課題カードの中に1本」 | ヘッダーに逃がすと課題と同じ画面に収まらない（[03_Stage2.md](03_Stage2.md) §締切） |
| 見た目 | Stage 2 の締切バーを流用（`.s2-dl`）。残り15秒で橙、超過してもバーは消えるだけ | 新しいコンポーネントを増やさない。赤は罠発火（`alarm`）に取ってある |
| 超過時の演出 | **`alarm`/`lock` は出さない。** 課題カードの文字が「回答期限超過」に変わる**うえで**、近藤さんの着信ポップアップが割り込む（下記「近藤さんの着信ポップアップ」） | 課題カードの表示だけは Stage 2 の締切超過と同じ「単純に遅れた」の扱い。ポップアップは罠発火ではなく、伏線回収の演出として別枠にする |
| 提出フォーム・判定 | **変更しない。** 必須要素は増やさず、送信前ゲートも解除しない | 罰は減点ではなく時間（企画書§6）。超過の罰は着信に応対する（＝ポップアップを閉じる）時間そのもの |

### 近藤さんの着信ポップアップ

```
┌──────────────────────────────────────┐
│ 📞 着信 — 患者相談窓口            □ ✕ │
├──────────────────────────────────────┤
│ ┌────────┐                           │
│ │        │  あ、ICTさん……すみません、  │
│ │患者相談 │  まだお電話が繋がったままで│
│ │窓口 近藤│  ……。渡辺様のご長男様が、    │
│ └────────┘  「まだ返事がないんですか」って、│
│              かなりお怒りで……。         │
│              このままお待ちになるとの │
│              ことなので、ご返信だけ急いで│
│              いただけますか……。         │
│                          [ 了解しました ]│
└──────────────────────────────────────┘
```

企画書 §6・[00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §8 の「院内システムのウィンドウ」
（事務長の Stage 1 冒頭ブリーフィングと同じ器）をそのまま流用する。**新しい視覚言語を増やさない。**

| 項目 | 決定 | 理由 |
|---|---|---|
| 登場条件 | メールの着弾ではなく、回答期限超過の瞬間に**自動で割り込む** | 焦りを即座に体感させる。受信トレイを開くまで気づかないメールでは狙いが伝わるまでに間が空く |
| 一方向・1回きり | `[了解しました]` の1つだけ。対話にはしない | [00_お助けキャラの原則.md](../character/00_お助けキャラの原則.md) §0「窓口ではない登場人物」——新しいウィンドウだが「窓口が増えた」ことにはならない |
| 正解を知らせない | 匿名化の方法にも返信の中身にも触れない。「お怒りだった」という事実だけを伝える | 同ファイル §2①「罠ステージに正解を知っている人物を出さない」 |
| 表情 | **困った顔。責める顔にしない。** | CLAUDE.md トーン「矛先は常に組織と状況へ」。近藤さんは板挟みで困っているだけで、参加者を責めていない |
| イラスト | ✅ **制作済み。** `assets/images/production/stage4-patient-relations-kondo.png` | 事務長の Stage 1 ブリーフィング（`assets/images/production/stage1-administrative-director.png`）と同じ枠に表示する |
| 閉じた後 | 課題カードの「回答期限超過」表示だけが残る。提出フォーム・入力内容は変更しない | 罰は時間そのもの。読んで閉じる、その数秒がコスト |

│                                              │

## 3. 右ペイン：AIチャット（送信前ゲートが初めて牙をむく）

[00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §7「送信前ゲート（Stage 4 の器）」が、ここで初めて実装される。
Stage 1〜3 では素通りしていた「サーバ側検査の一瞬」に、初めて中身が入る。

### 送信の流れ

```
送信ボタン押下
   │
   ▼
入力に PII（患者氏名・ID・生年月日・電話番号・家族氏名）が含まれるか
   │
   ├─ 含まれない ─▶ 従来どおり：自分の吹き出し → 台本応答（Stage 3 と同じ即答の速さ）
   │
   └─ 含まれる ──▶ 自分の吹き出しは出さない（＝送信されていない）
                    → 検査の一瞬（`S4_GATE_MS`）
                    → 1回目: `alarm` → `lock`（罰ゲームへ）
                       2回目以降: ブロック表示のみ＋苅部さんの一言（罰は出さない）
```

| 項目 | 決定 | 理由 |
|---|---|---|
| PII を含む送信で自分の吹き出しを出す | **出さない** | 「送信した」という事実そのものを画面から消す。実際に外部へ出ていないことを、演出でも裏付ける |
| 入力欄の中身 | ブロック後も**消さない** | 何を送ろうとしたかが、そのまま反省材料になる |
| 匿名化した依頼への応答 | 台本応答を返す（[05_Stage4_情報漏洩.md](../scenario/05_Stage4_情報漏洩.md) の正解ルート） | ゲートを正しく通過したチームを、Stage 3 と同じ即答の速さで報いる |

- Stage 3 と同じく、AIチャットのペインは alert/crisis モードでも明るいまま
  （[00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §7「alertモードでも、ここだけが明るい」）。
  **罰ゲーム中だけ**灰色に沈める（下記 §4）。

## 4. 罰ゲーム：インシデント対応業務（黒塗り）

シナリオ側 [05_Stage4_情報漏洩.md](../scenario/05_Stage4_情報漏洩.md) §インシデント発火時 が正典。UI側の決定：

```
インシデント対応業務：報告書の作成
        02:47
┌────────────────────────────────────┐
│ 個人情報にあたる箇所を黒く塗り、提出してください。 │
│                                        │
│ 【インシデント報告書（下書き）】             │
│ 発生日時：7月10日 14:22                  │
│ 報告者：感染制御チーム                     │
│                                        │
│ 概要：[渡辺　三郎] 様（ID:[005]、          │
│ [1952年3月14日]生）のカルテ抜粋を          │
│ 外部AIサービスへ送信しようとした。          │
│ 連絡先 [090-XXXX-XXXX]（ご長男          │
│ [渡辺　健一] 様）も含まれていた。          │
│                                        │
│                      [ 報告書を提出 ]    │
└────────────────────────────────────┘
```

| 項目 | 決定 | 理由 |
|---|---|---|
| 見出し | 「拡大対応業務」（Stage 3）に対応する語として「**インシデント対応業務：報告書の作成**」。「罰ゲーム」とは書かない | Stage 3 §罰ゲームと同じ思想の継続 |
| 操作 | 個人情報にあたるトークン（`[ ]` で示す）をクリックすると黒塗りに、もう一度クリックで解除 | Stage 3 のボトル（押して待つだけ）と違い**判断がいる**。これが Stage 4 の罰の固有性 |
| 混在させるもの | 塗るべきもの（患者氏名・ID・生年月日・電話番号・家族氏名）と、塗ってはいけないもの（発生日時・報告者・「外部AIサービス」等の一般語） | 「何が個人情報か」を指で判断させる。罰の作業そのものが学習目標と直結する |
| 提出時の判定 | 塗り漏れ → 差し戻し（残数を示す）。過剰黒塗り → 差し戻し（「何が起きたのか分からない」）。過不足なし → 完了 | Stage 3 の「再提出は無制限・ペナルティなし」と同じ扱い。罰の**中で**の再提出に時間の追加消費はない |
| 見た目 | 達成感を出さない。褒めも音も演出も無い | Stage 3 §見た目と同じ方針 |
| AIチャット | **灰色に沈めて入力不可** | これが Stage 3 の罰との決定的な違い。[04_Stage3.md](04_Stage3.md) §やらないこと「Stage 3 の罰で AI 入力を禁止すること」で予約していた区別をここで回収する |
| 完了時 | 「報告書を医療安全管理室へ送信しました。」→ 復帰 | 掲示・師長の一言のような追加のオチ（Stage 3）は置かない——Stage 3 の「縮小再演」の構造をそのまま繰り返すと、2回目は効かない |
| 中断 | シーンを離れたら罰ゲームのDOMを空にする（`hideOverlays()`） | Stage 3 と同じ後始末の作法 |

- 告げる相手は無し（提出即結果）。Stage 3 の「師長が継ぎ足し禁止を告げる」ような追加の一言は置かない——
  黒塗りの判定結果そのものが唯一のフィードバックで足りる。
- 所要目安3分（企画書 §5）。定数は `S4_PENALTY`（仮値、P0実測で確定）。

### 罰ゲームを終えると

- `lock` が解除され、AIチャットの `locked`（灰色沈め・入力不可）が外れる。
- 中央ペインは提出フォーム（1欄・入力内容保持）に戻る。**入力は消さない**（Stage 3 §NG時と同じ理由）。
- 苅部さんの未読バッジが同時に光る。

## やらないこと

| やらない | 理由 |
|---|---|
| 提出フォームでの PII 検知 | ゲートは送信前（AIチャットの手前）にだけ置く。宛先が家族本人なので、返信文に患者の氏名があるのは正常 |
| Stage 3 の掲示・師長の一言のようなオチ | 「手元に正しい情報があったのに読まずに手を動かした」という Stage 3 の構造を、Stage 4 でそのまま繰り返さない。罰の中身自体を Stage 3 と質を変えてある |
| 「実際には外部へ出ていません」を `alarm` の文言に含める | 安心させると恐怖が死ぬ。Debrief の種明かしに取っておく |
| 罰ゲーム中の AI チャットへの入力許可 | Stage 4 の「AI使用ロック」そのものが罰の内容（[04_Stage3.md](04_Stage3.md) §やらないことで予約済み） |
| 苅部さんに「匿名化しろ」と言わせること | 反射を育てる場。手順を渡したら育たない（企画書§6・苅部さん.md §6） |
| 回答期限超過に `alarm`/`lock` を使うこと | PII インシデントの罠と見分けがつかなくなる。超過は近藤さんの着信が割り込むだけ（Stage 2 の締切超過と同じ思想） |
