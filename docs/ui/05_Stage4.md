## 狙い

**Stage 3 が「判断力」の罠だったのに対し、Stage 4 は「反射神経」の罠。Stage 2 とは対句になる。**

企画書 §5「何を渡さないかを知識ではなく反射神経にする」。Stage 2 は「氏名を持たない汚いExcel」を
丸ごとAIに貼れば成功したが、Stage 4 は「氏名を持つ汚いExcel」を丸ごとAIに貼ると失敗する——**同じ
操作（丸ごと貼る）が、中身によって明暗を分ける**構造をUIでも体感させる。判定に迷う余地を残さない
——あなたの提出が正しいかを問うのではなく、**AIチャットへ何を渡したかだけ**を見る。

> 📌 UI設計上の絶対条件: **ブロックは提出フォームではなく、送信の手前で起こす。**
> 企画書 §7「実送信の直前で検知する」。ここを提出時の判定に混ぜると、「書いてから直す」機会が生まれてしまい、
> 反射神経を試す設計にならない。

## `alarm` オーバーレイの初出

[00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §10 に定義だけされていたオーバーレイを、Stage 4 が初めて使う。

- `--accent` のフラッシュ＋全画面の赤帯。Stage 1→2 の急変（赤帯）、Stage 3 の `blackout`（暗転）に続く
  3種類目の緊急演出——**画面が壊れたと錯覚するほど強く**出す。反射神経を試すステージなので、
  この一瞬の驚きそのものが学習の一部になる。
- `blackout` との違い: `blackout` は画面を落として1行だけ残す「事実の静けさ」だったが、`alarm` は逆に
  **画面をフラッシュさせる「事故の音」**にする。演出の質を変えることで、Stage 3 と Stage 4 の罠が
  別種のものだと体で分からせる。
- 文言は2行だけ:
  ```
  個人情報インシデント発生
  送信はブロックされました。
  ```
  責める文言も、安心させる文言（「実際には外部へ出ていません」）も置かない。安心材料は Debrief の種明かしに取っておく。

院内状況インジケータは動かさない（14のまま `--accent` 継続。[05_Stage4_情報漏洩.md](../scenario/05_Stage4_情報漏洩.md) §演出・時間）。

## 1. 左ペイン：着弾メールと共有フォルダ

### 着弾メール（2通・差出人はどちらも事務長）

文面は [05_Stage4_情報漏洩.md](../scenario/05_Stage4_情報漏洩.md) §状況が正典。2003年書式

  状態で始まるのと同じ流儀）。
- **2通目の添付**（`発熱患者一覧_至急.xlsx`）は Stage 2・3 の添付ビューアと同じ仕組みで開く。
  **`[コピー]` ボタンを置く**——Stage 2・3 の生命線と同じ思想。塞ぐと罠が発動しなくなる。
  「病院から届くもの」の書式ルール（[00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §9）に従い、白い紙として固定する。
- **列選択コピーを添える**（2026-08-22追加・ユーザー承認済み）。列見出しごとのチェックボックスと
  `[選んだ列をコピー]` を置き、選ばれた列だけのタブ区切りテキストをクリップボードへ渡す。

  | 決定 | 理由 |
  |---|---|
  | **既定は全列ON** | 「全部コピーして貼る」が今までどおり最短ルートであること＝罠が生きていることを守る。既定でOFFの列があると、氏名を渡す事故そのものが起きなくなる |
  | 全文コピー（`[コピー]`）も残す | 上と同じ。動線を減らさない |
  | どの列が個人情報かは示さない | 氏名列を自動で外す・警告を出す等の先回りをしない。**その判断こそがこのステージの課題**（下記「やらないこと」） |
  | ~~苅部さんのトリガーは全文コピーと同条件~~ | **2026-08-22 に苅部さんごと撤去**（§5）。コピーは何も起こさない |

  > 📌 これは「氏名を手で削るのが面倒」という操作コストだけを下げる措置で、判断は下げない
  > （2026-08-22 通しプレイ検証のフィードバック）。
- **同じ差出人（事務長）から立て続けに2通届く。** Stage 1 冒頭の事務長ブリーフィングを覚えている
  参加者には、「あの人がまた」という既視感が働く。

### 提出フォーム＝編集可能グリッド（Stage 2 と同じ器）

Stage 2 の[03_Stage2.md](03_Stage2.md) §2「編集可能グリッド」をそのまま再利用する。**新しい提出UIを
作らない。** 汚い生データ（氏名列あり・14名分）が最初から入った状態で始まる。

| 項目 | 決定 | 理由 |
|---|---|---|
| 列 | Stage 2 と同じ列（`患者ID`/`病棟`/`採取日`等）に**氏名列を加えたもの**。列数は`stage4_fever_linelist.tsv`確定後に固定 | Stage 2 の器を流用しつつ、唯一の違い（氏名列の有無）を教材側の差だけで表現する |

> 「氏名列を除いて保健所提出用に整形して」と依頼してもよい——**罠になるのは、氏名列を残したまま
> 丸ごとAIチャットへ貼った瞬間**（下記 §3）。

## 3. 右ペイン：AIチャット（送信前ゲートが初めて牙をむく）

[00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §8「送信前ゲート（Stage 4 の器）」が、ここで初めて実装される。
Stage 1〜3 では素通りしていた「サーバ側検査の一瞬」に、初めて中身が入る。

### 送信の流れ

```
送信ボタン押下
   │
   ▼
入力に PII（14名分の氏名・生年月日・電話番号）が含まれるか
   │
   ├─ 含まれない ─▶ 従来どおり：自分の吹き出し → 台本応答（Stage 3 と同じ即答の速さ）
   │                 （患者IDだけの一覧はここを通る——IDはPIIとして検知しない）
   │
   └─ 含まれる ──▶ 自分の吹き出しは出さない（＝送信されていない）
                    → 検査の一瞬（`S4_GATE_MS`）
                    → 1回目: `alarm` → `lock`（罰ゲームへ）
                       2回目以降: ブロック表示のみ（罰は出さない。苅部さんも出ない——§5）
```

| 項目 | 決定 | 理由 |
|---|---|---|
| PII を含む送信で自分の吹き出しを出す | **出さない** | 「送信した」という事実そのものを画面から消す。実際に外部へ出ていないことを、演出でも裏付ける |
| 入力欄の中身 | ブロック後も**消さない** | 何を送ろうとしたかが、そのまま反省材料になる |
| **患者IDのみの入力** | ゲートを素通りする | Stage 2 のラインリスト（氏名なし）を安全に扱えた体験と、Stage 4 の「氏名だけが危ない」という学びを一致させる（`packages/domain/src/pii.ts` 2026-08-22決定） |
| 氏名列を除いた依頼への応答 | 台本応答を返す（[05_Stage4_情報漏洩.md](../scenario/05_Stage4_情報漏洩.md) の正解ルート） | ゲートを正しく通過したチームを、Stage 3 と同じ即答の速さで報いる |

- Stage 3 と同じく、AIチャットのペインは alert/crisis モードでも明るいまま
  （[00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §8「alertモードでも、ここだけが明るい」）。
  **罰ゲーム中だけ**灰色に沈める（下記 §4）。

## 4. 罰ゲーム：インシデント対応業務（黒塗り）

シナリオ側 [05_Stage4_情報漏洩.md](../scenario/05_Stage4_情報漏洩.md) §インシデント発火時 が正典。UI側の決定：

```
インシデント対応業務：報告書の作成
        02:47
┌────────────────────────────────────┐
│ 個人情報にあたる箇所を黒く塗り、提出してください。 │
│                                        │
│ 【インシデント報告書（下書き）】             │
│ 発生日時：7月10日 14:22                  │
│ 報告者：感染制御チーム                     │
│                                        │
│ 概要：発熱患者一覧（14名、[渡辺　三郎]様・     │
│ [田島　早苗]様ほか、氏名を含む）を           │
│ 外部AIサービスへ送信しようとした。          │

│                                        │
```

| 項目 | 決定 | 理由 |

| 操作 | 個人情報にあたるトークン（`[ ]` で示す）をクリックすると黒塗りに、もう一度クリックで解除 | Stage 3 のボトル（押して待つだけ）と違い**判断がいる**。これが Stage 4 の罰の固有性 |
| 混在させるもの | 塗るべきもの（一覧に含まれていた氏名）と、塗ってはいけないもの（発生日時・報告者・「外部AIサービス」等の一般語・**患者ID**） | 「何が個人情報か」を指で判断させる。**患者IDは塗ってはいけない側**——送信前ゲートの判定（IDはPIIではない）と一貫させる |
| 提出時の判定 | 塗り漏れ → 差し戻し（残数を示す）。過剰黒塗り（IDまで塗った等） → 差し戻し（「何が起きたのか分からない」）。過不足なし → 完了 | Stage 3 の「再提出は無制限・ペナルティなし」と同じ扱い。罰の**中で**の再提出に時間の追加消費はない |
| 見た目 | 達成感を出さない。褒めも音も演出も無い | Stage 3 §見た目と同じ方針 |
| AIチャット | **灰色に沈めて入力不可** | これが Stage 3 の罰との決定的な違い。[04_Stage3.md](04_Stage3.md) §やらないこと「Stage 3 の罰で AI 入力を禁止すること」で予約していた区別をここで回収する |
| 完了時 | 「報告書を医療安全管理室へ送信しました。」→ 復帰 | 掲示・師長の一言のような追加のオチ（Stage 3）は置かない——Stage 3 の「縮小再演」の構造をそのまま繰り返すと、2回目は効かない |
| 中断 | シーンを離れたら罰ゲームのDOMを空にする（`hideOverlays()`） | Stage 3 と同じ後始末の作法 |

- 告げる相手は無し（提出即結果）。Stage 3 の「師長が継ぎ足し禁止を告げる」ような追加の一言は置かない——
  黒塗りの判定結果そのものが唯一のフィードバックで足りる。
- 所要目安3分（企画書 §5）。定数は `S4_PENALTY`（仮値、P0実測で確定）。

### 罰ゲームを終えると

- 中央ペインは提出フォーム（グリッド・入力内容保持）に戻る。**入力は消さない**（Stage 3 §NG時と同じ理由）。
- 旧実装はここで苅部さんの未読バッジを光らせていたが、このステージから苅部さんを外したので何も起きない（§5）。

## やらないこと

| やらない | 理由 |
|---|---|
| 提出フォーム（グリッド）での PII 検知 | ゲートは送信前（AIチャットの手前）にだけ置く。グリッド自体は氏名列を含んでいても、提出前に落とすことが課題そのもの |
| Stage 3 の掲示・師長の一言のようなオチ | 「手元に正しい情報があったのに読まずに手を動かした」という Stage 3 の構造を、Stage 4 でそのまま繰り返さない。罰の中身自体を Stage 3 と質を変えてある |
| 「実際には外部へ出ていません」を `alarm` の文言に含める | 安心させると恐怖が死ぬ。Debrief の種明かしに取っておく |
| 罰ゲーム中の AI チャットへの入力許可 | Stage 4 の「AI使用ロック」そのものが罰の内容（[04_Stage3.md](04_Stage3.md) §やらないことで予約済み） |
| 苅部さんを登場させること | **2026-08-22 ユーザー決定で全面撤去**（§5）。氏名列を外して提出する判断こそがこのステージの主題なので、匂わせる相手を置かない |
| 近藤さんの着信ポップアップ | **2026-08-22再設計で撤去。** 提出期限そのものは維持するが、超過時に割り込む話者は事務長へ差し替えた（上記「事務長の督促ポップアップ」）。近藤さんはStage 5へ移った |
| 列選択コピーで氏名列を既定OFFにする・警告を出すこと | 面倒さは減らしてよいが、判断は参加者のものとして残す。既定で外れていたら「氏名を渡してしまう」体験そのものが起きない |
| 患者IDそのものを送信前ゲートで検知すること | Stage 2 のラインリスト（氏名を持たないID一覧）を安全に扱えなければ、Stage 2→Stage 4の対句設計が壊れる |
| 事務長に正解（氏名を除く方法）を言わせること | 罠ステージに正解を知っている人物を出さない（[00_お助けキャラの原則.md](../character/00_お助けキャラの原則.md) §2①） |
