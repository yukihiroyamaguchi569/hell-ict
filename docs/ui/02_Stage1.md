## §0. 事務長ブリーフィング（Stage 1 の冒頭・全画面オーバーレイ）

> 📌 [00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §7「開始ブリーフィング」の
> Stage 1版。事務長がタスクとメール処理のルールを告げ、`[了解しました]` で時計とレースが始まる。

Prologue の受信トレイ3通を読み終えると自動で表示される。台詞は
[02_Stage1_平常運転.md](../scenario/02_Stage1_平常運転.md) §0 が正典。

> ⚠️ **器はまだ `peace`。** アウトブレイクは起きておらず、赤帯も出ていない。
> 転調が来るのは Stage 1 を**終えたあと**（[01_Prologue.md](01_Prologue.md)
> 「急変（Stage 1 を終えたあと）」）。この画面も、続く Stage 1 本編も、明るいまま進む。

### 構造

`.entry`（入室画面）と同型の**不透明な全画面オーバーレイ**を複製して使う
（`.veil` ベース、`position:absolute; inset:0; z-index:60`）。ヘッダーの時計も
リーダーボードも完全に覆い隠す——というより、**この時点ではまだどちらも出ていない**
（レースが始まるのは下記のとおり `[了解しました]` から）。

```text
┌──────────────────────────────────────┐
│  病院執行部　事務長                          │
│                                        │
│  ——ああ、派遣の皆さん。本日からでしたね…      │
│  （台詞、3〜4段落）                        │
│                                        │
│  ┌ 院内メールシステムのご利用について ──┐   │
│  │ ・60秒で自動削除／督促なし／…          │   │
│  └──────────────────────────┘   │
│                                        │
│                          [ 了解しました ]  │
└──────────────────────────────────────┘
```

- 「他の職員は5分ですが」の一句だけ橙（`--warn`）にする。赤は使い減りする資源で、
  赤帯とStage 3・4の罠に取ってある。
- 3つのルール（1通ごとの締切・督促なし・時間切れは返信不可）は台詞ではなく、
  2003年書式（`--font-legacy`）の**通達の枠**が担う。「アプリの説明」ではなく
  「病院から届いた文書」に見せるための書式選択（§6「チュートリアルを置かない」と同じ発想。
  ただし§6の記述自体は旧Stage1のもので現在は要更新——後述）。
- ボタンは `[ 了解しました ]` の1つだけ。選択肢が無いことがそのまま状況の説明になる。

### 出し方：一度に置かず、段落単位で出す

**この画面は動画にも音声にもしない。** 動くのは文字だけで、**出す順番と間**で押す。
ただし**話者の顔は静止画で出す**。

動画・音声にしない理由は2つ。**①** 尺を固定するので、読むのが速いチームは待たされ、
遅いチームは読み切れない。レース形式と正面から衝突する。**②** 会場は1部屋に複数チーム。
各チームが別々のタイミングで音を鳴らせば混線する（[00](00_共通シェルと通奏低音.md) §201 の
「通知音は出さない」と同じ判断）。静止画はどちらにも当たらない——尺を持たず、音も出さない。

**顔は宣伝トレイラー用に起こした画をそのまま使う**
（`assets/images/production/stage1-administrative-director.png`）。
以前はこれを**悪役の画**として退けていたが、**事務長を組織の顔として描く**方向に
正典側を改めたので、食い違いは解消した（[シナリオ §0](../scenario/02_Stage1_平常運転.md)）。
丁寧語のまま無茶を通す人物に、あの笑顔はむしろ合う。

> 📌 **顔が立っても「窓口は一つ（苅部さん）」は破れない。** 事務長は**一方向・1回きり**で、
> 相談を受け付けない（[お助けキャラの原則](../character/00_お助けキャラの原則.md) §0）。
> 相談できる顔は苅部さん一人のままで、彼には**顔を与えない**——与えた瞬間に、
> 事務長と同じ「登場人物」の重さを持ってしまう。

台詞は9つの `.beat` に分け、以下の時刻（ms）で1つずつ現れる（`BRIEF_BEATS`）。

| 時刻 | 出るもの |
|---|---|
| 0 | 事務長の顔（肖像＋「病院執行部／事務長」） |
| 400 | ——ああ、派遣の皆さん。本日からでしたね。ご足労さまです。 |
| 1200 | さっそくですが、まずはメール処理を……感染対策は、その後で結構です。 |
| 2000 | 内容は簡潔で結構です。ただし、先方に失礼のない文面で……（**ミッションの明示**） |
| 2800 | あ、ひとつだけ。うちのメールは、返信しないと消えます。 |
| **3600** | **他の職員は5分ですが**——優秀な皆さんなら…（橙・**一拍おく**） |
| 4300 | では、よろしくお願いします。 |
| 4700 | 通達の枠（2003年書式） |
| 5300 | `[ 了解しました ]`（**ウィンドウのフッターに固定**） |

**顔が最初に出る。** 名乗りより先に、誰が喋っているかを見せる——この人物が何を言うかを、
参加者は顔を見た時点で身構える。

- **間そのものが演出。** 丁寧な口調の気持ち悪さは「間」で効く。全部を一度に置くと、
  ただの説明文になって読み飛ばされる。とりわけ 2400 → 3200 の一拍が、
  「他の職員は5分」の落差を作る。
- **画面のどこかを押すと残りが即座に全部出る。** レースなので、演出のために数秒奪うのは
  割に合わない。読み終えたチームから先へ進める（`s1BriefAll()`）。
- `prefers-reduced-motion` では `later()` も transition も 0 になるため、
  結果として最初から全部出ている状態になる。**意図した挙動**。
- 数値は `BRIEF_BEATS` に定数化してある（[01_Prologue.md](01_Prologue.md) 実装メモの
  「ミリ秒単位で定数化し、テストプレイ後に数値だけ差し替えられるように」に従う）。

> ⚠️ **1280×720 にほぼ余裕がない。** 全ビートが出そろった状態で中身は約718px、
> 枠が720px（実測・スクロール不要）。**台詞を1段落でも増やすとボタンが画面外へ出る。**
> 3〜4人で1画面を囲む研修では、スクロールしないと押せないボタンは事故になる
> （[00](00_共通シェルと通奏低音.md) §1）。文言を足すときは必ず実測すること。

### タイミング（この画面の実装上の要点）

**締切のカウント開始（`s1Init()` が打つ `t0`）を、この画面を閉じた瞬間まで遅らせる。**
先に打つと、事務長の話を読んでいる間に1通目の60秒が減っていき、
「1分以内」と告げた本人の言葉が読んでいる間に破られることになる。
実装は `docs/ui/mock/index.html` の `renderStage1Flood()` / `s1Begin()` を参照。

**このボタンが、セッション全体のレースの起点でもある。** `[了解しました]` を押した瞬間に
3つが同時に動き出す（`s1Begin()`）。

| 動き出すもの | 実装 |
|---|---|
| 1通ごとの60秒締切 | `s1Init()` が `t0` を打つ |
| セッション全体の経過時間（32px の数字） | `startClock()` |
| リーダーボード帯（他チームの位置） | `.board` から `down` を外す |

**押すまでは、どれも動いていない。** 事務長の話を読んでいる間は時計も止まり、
他チームの位置も見えない——**焦らずに読める**。そして押した瞬間、全部が一斉に走り出す。
押した本人は「了解」しただけのつもりでいる。

> 📌 転調（`peace` → `alert`）はここでは起きない。急変は Stage 1 を終えたあとで、
> そのときレースは既に走っている。**転調で始まるものは何もなく、色が変わるだけ**
> （[01_Prologue.md](01_Prologue.md)「急変（Stage 1 を終えたあと）」）。

## 1. 左ペイン：10本の砂時計

**このステージの主役は左ペイン。** 中央でも右でもない。

| 要素 | 決定 | 理由 |
|---|---|---|
| 並び順 | **締切が近い順**（`live` を上、`due` の昇順） | 上から潰せばよい形にする。判断を1つ減らす |
| 残り時間 | `mm:ss` ＋ 進捗バー | 数字だけだと差し迫り方が分からない。バーだけだと正確さがない |
| 締切15秒前 | 文字とバーを**橙**（`--warn`）に | 赤は使わない（急変に取ってある）。[01_Prologue.md](01_Prologue.md) の色ルール |
| 時間切れ | `時間切れ・返信不可` と表示し、**一覧に残す** | 消すと「無かったこと」になる。**残骸を見せることが罰** |
| 通知音 | **鳴らさない** | 1部屋に複数チーム。着弾のたびに鳴ると会場が壊れる（[00](00_共通シェルと通奏低音.md) §5） |

**着弾は約6秒間隔**（0/4/8/13/18/23/29/35/41/47秒）。一覧の最上部に割り込み、1回だけ震える。

## 2. 中央ペイン：読んで、打つ

- メール本文は**2003年書式**（`--font-legacy`）。アプリは今日のものだが、病院から届くものは古い。
- 返信欄は**空**。定型文もテンプレートも置かない。1回目は手打ちしかない。
- `[ 送信する ]` を押すと即座に `返信済み` へ。確認ダイアログは**出さない**——1秒が惜しい場面で
  「本当に送信しますか？」を出すのは嫌がらせにしかならない。
- ヘッダーの `返信済み n / 10` だけが進捗。**スコアも星も出さない**（企画書§報酬設計）。

## 3. ヘルプ第1段階：AIを使えるようにする（1回目の失敗後）

固定タイマーではなく、**全通捌けずに1回目が終わったこと**が発火条件。

- 院内連絡先ウィンドウ（PHS）が鳴り、3行が **900ms 間隔**で1行ずつ届く。
  一度に3行出すと「システムメッセージ」に見える。**人が喋っている速度**で出す。
- 台詞は [../scenario/02_Stage1_平常運転.md](../scenario/02_Stage1_平常運転.md) §三幕構成 が正典。
- **この瞬間に右ペインのAIチャットを解放する。** ただし返信欄との連携は無い。AIの回答を読んで
  転記する操作は残り、使えるようになっただけではまだ間に合わない。

## 4. 2回目：AIあり・下書きなし

- 右ペインのAIチャットで、メールの要点や返信方針を尋ねられる。
- AIの回答を返信欄へ自動転記・貼り付けはしない。参加者は返信欄に自分で文面を入れる。
- **ここでも失敗させる。** 不足しているのはAIの知識ではなく、要点から返信下書きへ接続する機能だと
  体感させる。

> ⚠️ **ボタンの使用を強制しない。** 手打ちで送っても同じように `返信済み` になる。
> 「AIを使え」と迫った瞬間に、研修が押し付けに変わる。速さで分からせる。

## 5. ヘルプ第2段階〜3回目：下書き機能を解放する

2回目を捌けなかった後、苅部さんが「下書き機能も解放しました」と告げる。ここで初めて、
各メールに `[ 要点をAIに渡す ]` を出す。要点欄には文面でなく**要件**（例:「PDF送付でOK」）を書き、
12文字以上で下書きが返信欄に入る。AIの文面はそのまま送信でき、編集も可とする。

> 📌 未来として見せるのは、会話画面に回答が現れることではない。**要点を決めれば業務の返信欄に
> 下書きが入り、人が送信前の調整に集中できること**である。

### 本番実装計画：Tabで下書きを確定する

モックは現状のボタン操作のままとし、**本番アプリの3回目でのみ**要点入力欄にフォーカスがある状態で
`Tab` を押すと、要点の入力を確定して下書き生成を始められるようにする。マウス操作の
`[ AIに下書きさせる ]` も残す。チームでPCを囲む状況では、短い要件を書いた人がそのまま
キーボードだけで次の工程へ渡せることを優先する。

| 項目 | 振る舞い |
|---|---|
| 発火条件 | 要点欄にフォーカスがあり、`Shift` / `Ctrl` / `Alt` / `Meta` を伴わない `Tab` が押されたとき |
| 入力の条件 | 前後の空白を除いた要点が12文字以上なら、`Tab` の通常のフォーカス移動を止めて生成を開始する |
| 短い入力 | 生成せず、要点欄を保持したまま「もう少し具体的に」と表示する。`Tab` の通常動作も止めない |
| 生成中 | 要点欄・ボタンを二重送信できない状態にし、`下書き中…` を表示する。完了後は本文欄へフォーカスを移す |
| 代替経路 | ボタンのクリック、本文の手打ち、送信は従来どおり利用できる。`Shift + Tab` は通常の逆方向フォーカス移動を保つ |
| 表示 | 要点欄の近くに `Tabで下書きを作成` と常時示す。Tab本来の挙動を上書きするため、隠しショートカットにしない |

実装は要点欄の `keydown` で処理し、IME変換中（`isComposing`）は発火させない。生成APIへ渡すのは
メール本文と確定した要点だけとし、[scenario/02_Stage1_平常運転.md](../scenario/02_Stage1_平常運転.md)
「下書きに院内固有の事実を捏造させない」のシステム指示を適用する。

## 7. このステージでやらないこと

- **チュートリアルを置かない。** ルールは事務長の通達（§0）が全部言っている。
- **AIの使い方を講義しない。** 第1段階では使えるようにするだけ、第2段階では下書き機能を解放するだけで、
  速さの差を操作で分からせる。
- **赤を使わない。** 締切が迫っても橙まで。赤は急変（§∞）に取ってある。
- **解錠演出を出さない。** このステージは「終わる」のではなく「終わったと思わされる」。
  一拍あとに急変が来る（[01_Prologue.md](01_Prologue.md)「急変（Stage 1 を終えたあと）」）。

## 実装メモ

- モックは旧二幕構成のため、三幕構成の画面・メール・状態遷移は本番実装時に新設する。
- 本番の定数（各回の締切・安全弁・要点の最小文字数）はP0実測後に確定する。
- `s1Frame()` は 250ms 間隔。1秒間隔だと残り時間の減り方がカクつき、締切の緊張が落ちる。
