# Final：記者会見（UI設計）

**地獄のICT UI設計 / 目安15分・本編の最終ステージ・4欄フォーム**
親企画書: [../企画書.md](../企画書.md) ｜ シナリオ: [../scenario/07_Final_記者会見.md](../scenario/07_Final_記者会見.md) ｜ 器: [00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) ｜ 前段: [06_Stage5.md](06_Stage5.md)

> ⚠️ 参加者に見えるステージ名は **`Final　会見`**。「記者会見」は設計ドキュメント上の呼称と同じだが、
> ステージ名としては Stage 3「暫定」・Stage 4「回答」・Stage 5「掲示」と同じ短い体言止めに揃える。
> Final に罠は無いのでネタバレ回避の理由は無いが、呼称の一貫性としてこの形にする。

---

## 狙い

**Stage 3 の3欄フォームを、4欄に増やして最後にもう一度使う。** 新しい入力方式は増やさない——
`.box` ＋ `.submit-area` という同じ部品を1つ足すだけで、参加者は迷わず「また同じ形式か」と分かる。

UIの仕事は2つだけ：①4つの読み手向けの文章を、迷わず書き分けられる形で並べること、②通過したときに
**「次のステージへの解錠」ではなく「レースの終端」**だと一目で分かる演出を出すこと
（[../scenario/07_Final_記者会見.md](../scenario/07_Final_記者会見.md) §ゴール）。

---

## 画面全体

Stage 5 の3ペイン構成を踏襲する。**提出フォームが4欄フォームに戻る**のが変化点（Stage 3 の3欄を1つ増やした形）。

```
┌──────────────────────────────────────────────────────────────────────┐
│ 🏥 聖クロノス総合病院 ICT │ 原因不明の発熱 14               │ 83:40 │ B班 │
├────────────────┬────────────────────────────┬────────────────────────┤
│ 受信トレイ  2    │ ▸ Final  会見                │ AIチャット              │
│ ────────────  │ ────────────────────────  │ ┌ メイン ┐ ＋         │
│ ● 事務長        │ 明朝の記者会見に向けて、        │ ─────────────────  │
│   明朝の記者会…  │ 資料を作り提出せよ。            │  （まだ何もありません）│
│ ● 広報課         │                             │                      │
│   記者クラブか… │ ┌─ ①院長向け想定問答 ─────────┐ │ ─────────────────  │
│   📎 記者クラブ   │ │                          │ │ [           ][送信]  │
│      事前質問.txt│ └────────────────────────┘ │                      │
│                │ ┌─ ②ご家族向け説明文 ─────────┐ │                      │
│ 共有フォルダ      │ │                          │ │                      │
│  📄 発熱対応早見  │ └────────────────────────┘ │                      │
│     表.pdf       │ ┌─ ③職員向け通知 ────────────┐ │                      │
│  📄 院内感染対策  │ │                          │ │                      │
│    マニュアル.pdf │ └────────────────────────┘ │                      │
│                │ ┌─ ④報道機関向けリリース ──────┐ │                      │
│                │ │                          │ │                      │
│                │ └────────────────────────┘ │                      │
│                │              [ 提出する ]     │                      │
├────────────────┴────────────────────────────┴────────────────────────┤
│ Prologue ─ S1 ──── S2 ──── S3 ──── S4 ──── S5 ─── Final              │
│                                              ◆                        │
└──────────────────────────────────────────────────────────────────────┘
                                                    ┌──────────────────┐
                                                    │ 📞 院内連絡先      │
                                                    └──────────────────┘
```

**4欄 × textarea が 616px の中央ペインに収まらない。** Stage 3 の `min-height:70px` を3つ並べただけでも
既にペイン高さの大半を使っており、4つ目を同じ高さで足すと `[提出する]` ボタンがペインの外へはみ出す。
**中央ペインを縦スクロールさせる**（`overflow-y: auto`）。各欄の `min-height` は Stage 3 より小さい
`56px` を仮値にし、スクロールで全欄にアクセスできることを優先する——4欄を同時に見比べながら書く
必要は無く（読み手ごとに独立して書く課題のため）、スクロールを嫌って詰め込むと個々の欄が窮屈になる。

## 1. 左ペイン：着弾メールと共有フォルダ

### 着弾メール（2通）

文面は [../scenario/07_Final_記者会見.md](../scenario/07_Final_記者会見.md) §状況が正典。2003年書式
（`--font-legacy`）は継続。

- 初期表示は**1通目（事務長）を開いた状態**にする（Stage 3〜5 と同じ流儀）。
- **広報課のメール添付**（`記者クラブ事前質問.txt`）は Stage 3・4 の添付ビューアと同じ仕組みで開く。
  **`[コピー]` ボタンを置く**（[Stage 3](04_Stage3.md) §1 の生命線と同じ思想）。質問リストを AI へ
  貼って下書きさせる動線は正当であり、Stage 4 のような漏洩の罠がここには無いため——Stage 5 が
  `[コピー]` を置かなかった判断（動線を作る必要が無い）とは前提が違う。

### 共有フォルダ：Stage 3 から常設のまま、中身を増やさない

[06_Stage5.md](06_Stage5.md) §1「Stage 3 以降 常設のまま残る」を継続する。Final でも増やさない——
正典マニュアルは既に共有フォルダに並んでおり、③職員向け通知を書くにはそこから引けば足りる
（[../scenario/07_Final_記者会見.md](../scenario/07_Final_記者会見.md) §配布教材「確定している事実の
一覧は渡さない」）。

## 2. 中央ペイン：課題と4欄フォーム

### 課題カード

```
 明朝の記者会見に向けて、資料を作り提出せよ。
```

Stage 2〜5 と同じく1行に留める。必須要素（読み手ごとの書き分けの中身）は画面に出さない——
2通のメールと記者質問リストを読んで自分で組み立てる動機を残す。

### 4欄フォーム

`.box` ＋ `.submit-area` は Stage 3 の3欄フォームと同じ部品。見出しだけ変える。

```
┌─ ①院長向け想定問答 ──────────────────────────┐
│                                              │
└──────────────────────────────────────────────┘
┌─ ②ご家族向け説明文 ──────────────────────────┐
│                                              │
└──────────────────────────────────────────────┘
┌─ ③職員向け通知 ──────────────────────────────┐
│                                              │
└──────────────────────────────────────────────┘
┌─ ④報道機関向けリリース ──────────────────────┐
│                                              │
└──────────────────────────────────────────────┘
                                  [ 提出する ]
```

| 項目 | 決定 | 理由 |
|---|---|---|
| 欄の並び順 | ①想定問答 → ②家族向け → ③職員向け → ④報道向け | 事務長メールに列挙された順そのまま。判定が指す欄もこの順（`F_ORDER`） |
| 差し戻し時の強調 | 該当欄に `.warn`（橙の縁取り）を付ける | Stage 2〜4 と同じ「失敗に見せない」表現 |
| 差し戻し回数の上限 | 無し | Final に新たな詰みを作らない（[../scenario/07_Final_記者会見.md](../scenario/07_Final_記者会見.md) §判定） |

## 3. 右ペイン：AIチャットは通常の文章応答に戻る

Stage 5 の画像生成分岐（`s5Generate()`）は Final では使わない。Stage 3・4 と同じ台本方式の文章応答に戻る
（[../scenario/07_Final_記者会見.md](../scenario/07_Final_記者会見.md) §AIチャット）。

| 項目 | 決定 | 理由 |
|---|---|---|
| 送信前ゲート（PII検知） | **働かせない** | Final の固有情報は「AIに送るな」ではなく「報道向けに書くな」の話。判定は④の欄が持つ |
| 応答の型 | 台本方式（`F_REQUEST_TRIGGER` → `F_AI_REPLY`）。断定調の会見文を返す | そのまま貼ると①④の未確定明示チェックに当たって差し戻される |
| ペインの明るさ | Stage 3・4・5 と同じく alert/crisis でも明るいまま | [00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §7 |

## 4. ゴール：`unlock` ではなく専用オーバーレイ `#ov-goal`

シナリオ側 [../scenario/07_Final_記者会見.md](../scenario/07_Final_記者会見.md) §ゴールが正典。

4欄すべてが判定を通過したら、Stage 2〜5 の `unlock` オーバーレイとは**別の器**を開く——
「次のステージを解錠した」ではなく「レースが終わった」ことを見た目で区別するため。

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                        │
│               Prologue ─ S1 ─ S2 ─ S3 ─ S4 ─ S5 ─ Final              │
│                                                        ◆              │
│                                                                        │
│                        B 班　ゴール                                   │
│              聖クロノス熱（仮）記者会見資料 — 提出完了                  │
│                                                                        │
└──────────────────────────────────────────────────────────────────────┘
```

| 項目 | 決定 | 理由 |
|---|---|---|
| 見た目の骨格 | h48 のリーダーボード帯を全画面サイズに拡大した構図 | [00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §5「首位が Final をクリアすると帯が全画面に展開」をそのまま絵にする |
| 停留所トラック | `Prologue…Final` の7停留所をもう一度描き、`◆` が `Final` にいる状態を大きく見せる | 帯の拡大版という体裁を保つ |
| 見出し | `B班　ゴール` | 「解錠しました」ではなく到達そのものを告げる |
| 副題 | `聖クロノス熱（仮）記者会見資料 — 提出完了` | 縦軸の仮称を最後にもう一度出す |
| 自動クローズ | **しない** | `unlock` は1900msで自動的に閉じるが、`#ov-goal` はゲームの終端なので閉じる理由が無い。参加者が見続けられる |
| 音 | 鳴らさない | モックには一度も音の実装が無く、Final だけ鳴らすと器の一貫性が崩れる。**本番はファンファーレを付ける**（実装メモ） |
| 下位チームの扱い | 匿名のまま（`TEAMS` は静的） | [00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §5「マーカーは出すが匿名にする」を維持 |
| 発熱インジケータ | 動かさない（14のまま） | [../scenario/07_Final_記者会見.md](../scenario/07_Final_記者会見.md) §演出・時間 |

## やらないこと

| やらない | 理由 |
|---|---|
| カウントダウン・締切バー | 実カウントダウンは Stage 4 だけの特権。Final に罠は無い |
| `alarm`/`lock`/`blackout` | Final に罠も罰も無い（Stage 5 に続き本編で2番目） |
| 差し戻し回数の上限 | 新たな詰みを作らない（企画書 §6「敗北条件はなし」） |
| 必須要素を画面に列挙すること | Stage 2〜5 と同じ理由。2通のメールと質問リストを読んで自分で言語化する動機を残す |
| 苅部さんに書きぶりを言わせること | [苅部さん.md](../character/苅部さん.md) §4「言えないこと：書きぶりそのもの」 |
| 他チームの追走アニメーション | ゴール演出は自チームの到達を見せるだけに留める。他チームの動きは通常のリーダーボード（下段の帯）に委ねる |
| Debrief 画面の実装 | Debrief はファシリテータ運用。Final の実装範囲はゴール演出まで |

## 実装メモ

- **判定は4欄それぞれのルールベース＋差し戻し。** Stage 2〜4 のような判定関数（`checkStageN()`）を
  4欄版として実装する——Stage 5 のような「判定そのものが無い」形とは違う（[../scenario/07_Final_記者会見.md](../scenario/07_Final_記者会見.md) §判定）。
- 教材の正典は [`../materials/final_press_questions.md`](../materials/final_press_questions.md)（記者クラブ
  事前質問。Markdown が正典、添付テキストは派生物）。
- ④の誤り判定（患者の固有情報）は Stage 4 の `S4_PATIENT`／`S4_PII` をそのまま参照する。新規の教材・
  検知パターンを作らない。
- 定数は `F_ORDER`（判定順）、`F_REQUIRED`／`F_WRONG`（4欄の必須語・誤り語）、`F_KARUBE_DELAY`
  （苅部さんの1段目トリガーまでの待ち秒数・仮値40秒）。すべて仮値、P0実測で確定。
- クレッシェンドの数値（14で継続）は [00_共通シェルと通奏低音.md](00_共通シェルと通奏低音.md) §4 と同期させる。
- **ゴール演出（`#ov-goal`）にファンファーレの音を付けるのは本番のみ。** モックは無音のまま実装する。
