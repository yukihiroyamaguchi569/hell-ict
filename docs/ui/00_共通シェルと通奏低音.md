# 共通シェルと通奏低音（UI設計）

**地獄のICT UI設計 / 全画面の器**
親企画書: [../企画書.md](../企画書.md) ｜ 縦軸: [../scenario/00_未知ウイルスの通奏低音.md](../scenario/00_未知ウイルスの通奏低音.md)

---

## 狙い

**全ステージが同じ器の上で動くようにする。** ステージごとに新しい画面を作らない。
器（シェル）は固定し、中身とテーマモードだけが差し替わる——この構造にしておけば、
Stage 3 の暗転も Stage 4 の警報も、後から新しい画面を起こさずに足せる。

シナリオ側には「明るいUI」「アクセントカラーが警告色に転じる」「リーダーボードが起動する」と
文章では書かれている。それを**実際に作れる粒度**まで落とすのがこのファイル。

## 1. 最大の制約：1画面を3〜4人で囲む

企画書 §3（PC1台・3〜4人編成）・§9（手持ち無沙汰リスク）が繰り返す前提。**この一点から画面設計のほとんどが決まる。**

### 従うべき3つの帰結

| 帰結 | 理由 |
|---|---|
| **3ペインを同時表示する。タブで隠さない** | 3〜4人が同じ画面のどこを見ているか分からない。課題文・AIチャットの出力・提出内容を常に同時表示し、誰かが見落とすことをタブ切り替えで作らない |
| **文字は1人用アプリより一段大きい** | 3〜4人が1画面を囲むと、両端の人は斜めから遠目に見る。標準的な16px基準では読めない |
| **ホバー・ドラッグに機能を載せない** | PCに触れるのは常に1人だけ。他は指差しで指示する。触れていない人には見えない操作性に機能を依存させない |

### 文字サイズの基準

1人用Webアプリの慣習値に **+2px** を基準とする。

| 用途 | サイズ | 備考 |
|---|---|---|
| メール本文・課題文・AIの応答 | **18px** | 読ませるものはすべてこれ以上 |
| UIラベル・ボタン | 16px | |
| メタ情報（送信時刻、行数など） | 14px | **これが下限。**これ以下を作らない |
| 経過時間 | 32px / 等幅 | 部屋の後ろからでも読める。時間が通貨だから最も大きい |
| ステージ名 | 20px | |

上の表を標準として、ヘッダーに **3段階の文字サイズ切替（A−／A＋）** を置く。標準・大（1.15倍）・特大（1.3倍）で、
倍率が掛かるのは読ませるもの——病院から届くもの（受信トレイの一覧と本文）・AIチャット・院内連絡先・課題文・
提出欄と判定文——に限る。ヘッダー・リーダーボード帯・ペインの固定幅・ボタンの高さは段階で変えない
（ファシリテーターが「画面の右下」と言える配置を段階で動かさないため）。設定は端末に保存し、リロードで維持する。

### 基準解像度

**1280×720** で設計する。会場のノートPCとプロジェクタ投影の最小公倍数であり、
宣伝トレイラー（1280×720）とも揃う。これより広い画面では中央ペインが広がるだけにする。

```
├────────────────┴────────────────────────────┴────────────────────────┤
│ リーダーボード帯 h48   ●━━━━━━━━━◆━━━━━━━━○━━━━━━━━━━━━━━━━━━━      │

                                                    └──────────────────┘
```

高さの内訳: `720 − 56（ヘッダー） − 48（リーダーボード） = 616` が3ペインの高さ。

### 3ペインが揃うのは Stage 1 の途中から

上の図は**完成形**であって、初期状態ではない。右ペインは最初から画面にいない（§7「登場」）。
それまでは中央ペインが右端まで伸びた**2ペイン**で、幅の内訳はこうなる。

| 局面 | 左 | 中央 | 右 |
|---|---|---|---|
| 入室・ウェルカム | なし | 1280 | なし |
| 受信トレイ〜Stage 1 前半 | 260 | **1020** | なし |
| Stage 1・ヘルプ第1段階以降 | 260 | 640 | 380 |

中央ペインは 1020px でも成立させること。本文には `max-width: 62ch` を効かせ、
**幅いっぱいに文字を流さない**。1画面を3〜4人で囲むので、長すぎる行は行頭に戻れなくなる。

### ペインを固定幅にする理由

左右を可変にすると、チームごとに違う画面幅で研修が進み、**ファシリテーターが「画面の右下を見て」と言えなくなる**。
40名が同じ画面配置を共有していることは運営上の資産なので、左右は固定し、中央だけ伸ばす。

## 3. テーマモード：転調は色ではなくトークンの入れ替えで起こす

急変を「赤い帯を出す」という**追加**では作らない。
**器の色そのものを差し替える**。CSSカスタムプロパティを定義し、
ルート要素の `data-mode` を切り替えることで画面全体が一斉に転調する。

```text
data-mode="peace"  → 平時（Prologue と Stage 1。急変が来るまで）
data-mode="alert"  → 警戒（Stage 2〜。本編のほぼ全て）
data-mode="crisis" → 危機（Stage 3 以降。今回は定義のみ）
```

> 📌 **`peace` は Stage 1 の終わりまで続く。** 平和な色のまま1分刻みのメール処理を
> やらされる居心地の悪さが Stage 1 の持ち味で、転調はそれを終えたあとに来る
> （[01_Prologue.md](01_Prologue.md)「急変（Stage 1 を終えたあと）」）。

### トークン定義

| トークン | peace | alert | crisis | 用途 |
|---|---|---|---|---|
| `--bg` | `#f5f1e8` | `#14171a` | `#08090a` | 画面地色 |
| `--surface` | `#fffdf8` | `#1e2226` | `#101112` | カード・ペインの面 |
| `--surface-2` | `#efe9dc` | `#272c31` | `#17191b` | 一段沈んだ面 |
| `--fg` | `#2b2724` | `#e8ecef` | `#d8dce0` | 本文 |
| `--fg-muted` | `#6f6559` | `#8d979f` | `#6b7176` | メタ情報 |
| `--accent` | `#3f7d78` | `#c1121f` | `#e01e2b` | 強調・進行 |
| `--rule` | `#ddd5c6` | `#2c3238` | `#1e2022` | 罫線・境界 |
| `--ok` | `#3f7d78` | `#3fa66b` | `#3fa66b` | 判定通過・解錠 |
| `--warn` | `#b8862b` | `#d99a1f` | `#d99a1f` | 罰ゲーム・ロック |

`alert` と `crisis` の基本色は宣伝トレイラーのビジュアルルール（黒・チャコール・冷たい白・深紅）と同じ。
**宣伝で見た世界に、そのまま入る**ようにする。

### OSのダークモードに従わない

`prefers-color-scheme` は**参照しない**。モードを支配するのはゲームの進行であって、参加者のOS設定ではない。
平時に警告色が出たり、急変が起きても画面が明るいままでは演出が死ぬ。

### 転調のアニメーション

`peace → alert` は 900ms かけて全トークンを補間する。瞬間的に切り替えると「画面が壊れた」に見える。
補間中にアラーム音・赤帯が重なることで「切り替わった」ではなく「**変わってしまった**」に見せる。
詳細は [01_Prologue.md](01_Prologue.md) §急変。

## 4. 院内状況インジケータ ＝ 通奏低音の実体

**縦軸ファイル（`docs/scenario/00`）は台帳であって固有の画面を持たない。**
その代わり、縦軸をUI上で担うのがこのインジケータ。ヘッダー中央に**全ステージを通して常駐**する。

```
在院 398/400 ・ 空床 2 ・ 本日入院 7 ・ 原因不明の発熱 3
```

- 14px、`--fg-muted`、等幅。**院内ダッシュボードの残骸**という体裁。
- 平時の指標（在院・空床・入院）に**紛れ込ませる**。単独で置いたら気づかれてしまう。

### クレッシェンドの表現

| 局面 | 表示 | 見た目 |
|---|---|---|
| Prologue 〜 Stage 1 〜 急変 | `原因不明の発熱 3` | 他の指標と完全に同じ。**誰も気に留めない**（`docs/scenario/01`「ここで警戒させたら設計失敗」）。急変で `alert` へ転調しても数字は変わらない（[01_Prologue.md](01_Prologue.md)「転調でも変わらない」） |
| Stage 2 解錠 | `原因不明の発熱 9` | まだ `--fg-muted`。数字が変わる瞬間だけ `.bumped` で1回だけ薄く光る（実装済み・[03_Stage2.md](03_Stage2.md) §3） |
| Stage 3 開始 | `原因不明の発熱 9` | **この項目だけ `--accent` に変わり、他の指標が消える**（`.vitals.crescendo`）。複数アウトブレイクの新たな火急さを示す |
| Stage 3 罠発火 | `原因不明の発熱 12` | 提出の誤りで対応が遅れたことを示す。罠を踏んだチームだけが経由する（[04_Stage3.md](04_Stage3.md) §3） |
| Stage 3 解錠 | 罠発火が無ければ9のまま、発火していれば12のまま据え置き | 踏んだチームも踏まなかったチームも、次のStage 3.5開始の演出でここが揃う |
| Stage 3.5 開始 | `原因不明の発熱 14` | Stage 2から残っていた縦軸が前面化し、ヘッダーの焦点を切り替える。クリア後も値は動かさず、「次の接点を減らした」結果だけを示す |
| Stage 4 開始 | `原因不明の発熱 14` | Stage 3.5から継続。保健所への発熱患者一覧（14名）提出要請で、院外にも知られ始めたことを示す（2026-08-22再設計：旧「家族からの問い合わせ」から変更） |
| Stage 5・Final | 継続 | `--accent` のまま |
| Final | 継続 | 会見の論点そのものになる |

> 📌 **Stage 2〜3の指標は「原因不明の発熱」1系統のまま**であり、Stage 3が疥癬（かいせん）版に
> 改訂された際も指標を切り替えていない（旧・ノロウイルス版で使っていた `5B病棟 胃腸炎` という
> 別ラベル・別数値系列〔5→8→10〕は廃止済み）。**疥癬は発熱を来さない**ため、罠発火時の9→12という
> 数字の動きは疥癬の重症化や既知アウトブレイクの拡大を意味するものではなく、**罠を踏んだことを
> 示す演出専用の共有カウンタの明滅**である（[04_Stage3_嘘.md](../scenario/04_Stage3_嘘.md) §演出・時間
> 実装メモ）。原因不明の発熱そのものの縦軸（Prologueの3名・Stage 2の伏線3名）とも症状面では
> 交わらない——Stage 3の患者3名と謎の発熱の患者3名は別人物のまま最後まで区別される。

### Debrief での回収

「この数字、**初日から画面の一番上にありました**。誰か見ていましたか？」
——インジケータの値の推移をサーバに残し、Debriefで再生できるようにする。

### Prologue の発熱3名と Stage 2 の伏線3名は同一人物とする（決定）

Prologue の夜勤師長メール（「原因不明の発熱の患者さんが数名」）の3名と、
Stage 2 の配布ラインリストに仕込まれた**MRSA陰性なのに発熱ありの3名（患者ID `005` / `6` / `008`）**は
**同一人物として扱う**。理由と回収経路は `docs/scenario/00_未知ウイルスの通奏低音.md` §3 が正典
（回収の経路は [00_未知ウイルスの通奏低音.md](../scenario/00_未知ウイルスの通奏低音.md) §3 が正典）。

- Stage 2 解錠時のインジケータ増分（3 → 9。上の§4クレッシェンド表と同じ値）は、**この3名とは別の
  新規6名**によるものとする——
  伏線の3名は Prologue から**値としては動かない**まま、Stage 4で保健所への発熱患者一覧（14名）
  提出要請が入って初めて表に出る（2026-08-22再設計：旧「患者005の家族から問い合わせ」から変更）。
- Stage 4の値（14）は、この決定を前提に組んである（上表）。

## 5. リーダーボード帯

画面最下部に常駐（Prologue では非表示。**事務長ブリーフィングの `[了解しました]` を押した
瞬間**に下からせり上がって出現する＝Stage 1 の開始と同時。急変ではない——急変が来る頃には、
レースはもう始まっている）。

```
 Prologue      S1        S2        S3        S4      S5     Final     ← 上段：停留所
                         ◆けんしょう班                              ← 下段：自チーム
```

### 表示ルール

| 対象 | 表示 |
|---|---|
| 自チーム | `◆` ＋ チーム名（入室時にチーム自身が入力したもの）。`--accent` で強調 |
| 首位チーム | `●` ＋ チーム名 |
| その他のチーム | `○` のみ。**名前を出さない** |

> ⚠️ **モックは自チームのマーカー1つしか描かない**（2026-08-22 ユーザー決定）。上の3行の表示ルールは
> **他チームの位置が実データで届く本実装の仕様**であり、モックにはその配信経路が無い。ダミーの他班
> （A班・D班…）を並べていたときは、入室時にチーム自身が入力した名前がヘッダーのチップと感謝状には
> 出るのに、帯だけが作り話の並びを見せていた——**同じ画面で名前が食い違うくらいなら、正直に自分の
> 位置だけを出す**。停留所ラベルは7つとも残す（自分がどこまで来たかは、それだけで読める）。
> **他チームのライブ表示は本実装の宿題**——全体用 Durable Object から配信する（企画書§7）。
> それが乗った時点で、上の3行がそのまま生きる。

**停留所ラベルは上段、チームのマーカーは下段**に分ける。帯は48pxしかないので、
同じ行に重ねるとラベルとマーカーが必ず衝突して、誰がどこにいるのか読めなくなる。
同じ停留所に複数チームがいる場合は、マーカーを横に等間隔で散らす。

**下位チームを名指しで晒さない。** 企画書§5は「先行チームの位置が見えて焦りを演出する」と明言しており、
焦りは意図した効果なので位置マーカーは全チーム出す。一方で§9は「後続の心が折れる」を大リスクに挙げている。
**マーカーは出すが匿名にする**ことで、焦りは残し、羞恥だけを取り除く。

### 動き

- 他チームが解錠すると、そのマーカーが**滑らかに右へ移動**する。通知音は出さない（気づいた人だけが焦る）。
  ——**モックでは自チームの移動だけが見える**（上の ⚠️）。滑らかに動く仕掛け（`.mark-t` の `left` の
  トランジション）はそのままなので、他チームの配信が乗れば追加実装なしで動く。
- 首位が Final をクリアすると帯が全画面に展開し、ファンファーレとともに優勝告知（企画書§5）。

## 6. 院内連絡先ウィンドウ（お助けキャラ）

企画書 §6 の絶対条件——**「嘘つきGPT-4o」とは別人格・別UI**——を、見た目で徹底する。

### 相手は既定で固定、ただし替わりうる

**既定の話し相手は情シスの苅部さん**（[../character/苅部さん.md](../character/苅部さん.md)）。
ログは**ステージをまたいで連続させる**。相談履歴が積み上がっていくこと自体が、
120分を通して同じ人物と付き合っている感覚になる。

シナリオ上どうしても別の職種が要る回は、**苅部さんが同じウィンドウの中で電話を回す**
（[../character/00_お助けキャラの原則.md](../character/00_お助けキャラの原則.md)）。
窓口を増やさないので、器としては以下だけ用意しておけばよい。

| 項目 | 決定 |
|---|---|
| 話者の区別 | `〔苅部〕` `〔みどり〕` の**前置きだけ**で区別する |
| **吹き出しの形・色は話者で変えない** | AIチャットとの差が本質で、人間同士の差は本質ではない。人ごとに色を付けると「キャラUI」になり、企画書§6の別人格・別UIが薄まる |
| 名前欄 | `情シス 苅部` → `5A病棟 みどり師長（苅部さんが取り次ぎ）`。ゲストが去れば戻る |
| 取り次ぎの表示 | ログに区切り線＋1行（`── 苅部さんが5A病棟へ転送しました ──`）。演出はここだけ |

> 📌 **会話ログのレコードには `speaker` を最初から持たせる。** 話者が1人しかいない今のうちに入れておく。
> 後から足すとログのスキーマ変更になり、既に走ったセッションの記録が読めなくなる。

### 別ウィンドウとして描く

右ペインのAIチャットと**同じ吹き出しUIを絶対に共用しない**。共用した瞬間に
「AIも先輩も同じチャット」に見え、テーマ（AIは嘘をつく／人間と正典は正しい）が濁る。

置き場所は**中央ペインの右下**（右ペインの左隣）。「画面の右下」に置くと
AIチャットの入力欄の上に被さり、入力を塞ぐうえ、AIと先輩が同じ場所にいるように見える。
**AIチャットには一切重ねない。**

```
折り畳み時（中央ペインの右下 w220 h44）  展開時（w320 h420）
┌────────────────────┐              ┌────────────────────┐
│ 📞 院内連絡先    ①  │              │ 📞 院内連絡先    ✕ │ ← 緑のタイトルバー
└────────────────────┘              ├────────────────────┤
                                    │ 情シス 苅部           │
                                    │ ────────────────── │
                                    │ 〔苅部〕今、別病棟対応中。│
                                    │      あとで。         │
                                    │                    │
                                    │ ────────────────── │
                                    │ [            ][送信] │
                                    └────────────────────┘
```

| 項目 | AIチャット（右ペイン） | 院内連絡先（別ウィンドウ） |
|---|---|---|
| 位置 | ペインとして画面に組み込まれている | 画面右下に**浮いている**。閉じられる |
| 色 | 明るい面（後述） | 緑のタイトルバー `#1f6b3f`、白背景 |
| 書式 | 現代的な吹き出し | **2003年風**。角丸なし、`〔名前〕` 前置きの平テキスト |
| 応答 | 即座 | **遅延**（サーバ側タイマー）。先に未読バッジだけが赤く光る |
| 中身 | 万能。ただし嘘をつく | 観点と問いだけ。正解は言わない |

### 遅延がヒントのコストになる

企画書§6「待たされ＝ヒントのコスト＝時間」を、UIでは**未読バッジが先に光り、開いても返事がまだ来ていない**
という形で表現する。「相談したのに待たされる」を体験させる。返信が届いたら再度バッジが光る。

### 滞留トリガー

規定時間そのステージに留まると、**向こうから先に**声をかける（企画書§6）。
このとき自動でウィンドウを開かない。**バッジが光るだけ**にする。
勝手に開くと「アプリがヒントをくれた」になり、参加者が自分でプロンプトを打つ練習が死ぬ。

## 7. 全ステージ共通：開始ブリーフィング

**Stage 1〜Final は、各ステージの作業画面を出す前に必ず開始ブリーフィングを表示する。**
依頼者の顔写真とメッセージを大きく出し、参加者が `[了解しました]` を押して初めてそのステージを開始する。
Prologue は入室・導入であり課題ステージではないため、この規則の対象外とする。

これは操作説明ではない。誰から何を頼まれ、どの制限の中で動くかを、**病院の中の人物が直接伝える**ための
物語上の入口である。Stage 1の事務長、Stage 2の看護部長はこの共通仕様の先行例とする。

| 項目 | 共通ルール |
|---|---|
| 表示 | シェル全体を覆う不透明なオーバーレイ。左に依頼者の顔写真、右にメッセージ、下端に `[了解しました]` だけを置く |
| 伝えること | 状況の一文、タスク、制限時間または重要な制約、締切超過時の扱い。参加者が開始直後に迷わない最小限に絞る |
| 伝えないこと | 正解、解法、AIへの依頼文、罠の存在や発火条件。Stage 3・4では特に、検証すべき内容を先回りして言わない |
| 時間 | Stage 1では `[了解しました]` がレース時計の開始点。Stage 2以降では、レース時計は継続させたまま**ステージ固有の締切・遅延ヒント**をこのボタンから開始する。読む時間でステージの持ち時間を失わせない |
| 閉じた後 | 依頼のメール・添付・課題カードを作業画面に残す。ブリーフィングで聞いた内容を、あとから確認できるようにする |
| 人物 | 依頼の当事者を原則とする。顔写真は本番用アセットとして制作し、苅部さんはこの役を担わない |

> 📌 一律のテンプレート文にはしない。依頼者の口調と事態の温度は各ステージで変えるが、
> **「顔のある依頼 → ルールの明示 → 了解して時計が動く」**という順序だけは共通にする。

## 8. AIチャットペイン

### 登場：Stage 1のヘルプ第1段階で使えるようになる

**右ペインはStage 1の1回目の間は存在しない。** 中央ペインが右端まで伸びている。
1回目の失敗後、苅部さんがAIチャットを使えるようにする。ただし、この段階では返信欄への下書き連携は無い。
2回目の失敗後に下書き機能が解放される（[02](02_Stage1.md) §3〜§5）。

道具を先に置かず、手打ちで間に合わないことを先に経験させる。次に「AIが使える」だけでは
転記に時間を失うことを経験し、最後に下書き連携を渡す。この順序が、メール返信の未来を体験させる。

| | |
|---|---|
| 出現アニメーション | 右から 420ms でスライドイン。中央ペインが押されて狭くなる |
| **説明を出さない** | 「AIが使えるようになりました」等のトーストを出さない。苅部さんの台詞が現れることの説明を兼ねる |
| 初期状態 | ログは `（まだ何もありません）`。挨拶もサンプルプロンプトも出さない |
| 一度出たら引っ込めない | Stage 1で出てからは以降のステージでも常設。罰ゲーム中だけ灰色に沈める（§10 `lock`） |
| 苅部さんの先触れ | 1回目の失敗後に、使えるようにしたことを本人の台詞で伝える。パネルが先、解放の理由が後にならないようにする |

### alert モードでも、ここだけが明るい

チャコールの画面の中で、**AIチャットのペインだけが白く光っている**。

これは演出。参加者の視線は自然にそこへ吸い寄せられ、「この暗い病院で、ここだけが頼れる」という
体感を作る。Stage 3 で、その明るい場所から嘘が出てくる。

`--surface` を使わず、専用トークン `--ai-surface: #f7f9fa` / `--ai-fg: #1a1d20` を全モード共通で持つ。
（`crisis` モードでもここは明るいまま。Stage 3 の暗転演出は、この明るさとの対比で効く）

### スレッドタブ

企画書§7「チームに1契約、ただし会話スレッドは複数」。ペイン上部にタブを並べる。

- スレッドの実体（`メイン`1本）はStage 1のヘルプ第1段階で右ペインとともに現れる。右ペインごと無い
  1回目にはタブも無い。Stage 2以降は「1本だけ」の状態から継続し、増えても驚かせない。
- タブ名はチームが自由に付けられる（Stage 2 の「タスクごとに文脈を分離」を促すため）。
- 「＋」で新規スレッド。上限は設けないが、4本を超えたらタブが縮む。
- **ステージへ入場するたび、そのステージ名のスレッド（`Stage 2`〜`Stage 6`）へ自動で切り替える**
  （2026-08-22ユーザー決定）。**Finalは対象外**——右ペインごと畳んで送信経路が無いステージなので
  （[07_Final.md](07_Final.md) §1）、開けないスレッドだけがサーバに増えるのを避ける。
  無ければ作り、同名が既にあれば作らず切り替えるだけにする——devbarのジャンプや
  リロード復帰でタブが増殖しないため。**履歴は消さない**。前のステージのタブはそのまま残り、いつでも読み返せる
  （サーバ保存は予備PCからの復帰の柱なので、削除ではなくスレッド分割で仕切り直す）。
  作成に失敗したときは現行スレッドのまま静かに続行し、進行を止めない。

### 送信前ゲート（Stage 4 の器）

送信ボタン押下から実際の送信までの間に**サーバ側検査の一瞬**を挟む設計にしておく。
Stage 1〜3 では素通りするが、Stage 4 の PII 検知（企画書§7・**OpenAIへ送る前にWorkers側で止める**）が
ここに入る。**この隙間を最初から空けておく**こと。後から差し込むと、送信済みの見た目を巻き戻す羽目になる。

## 9. 「病院から届くもの」は2003年の書式で描く

電子カルテ2003年製というブラックユーモアを、配色ではなく**書式**で効かせる。

| 区分 | 見た目 |
|---|---|
| **アプリのシェル**（ヘッダー・リーダーボード・AIチャット・提出フォーム） | 現代的。角丸、余白、可変フォント |
| **病院から届くもの**（メール本文、配布Excel、院内マニュアルPDF、判定エラー文、院内連絡先） | **2003年**。等幅寄り、角丸なし、罫線、`【至急】`のような全角括弧、`MS Pゴシック` を思わせる字面 |

### 「ファイル」はテーマに追従させない

配布Excelのビューアと院内マニュアルPDFのビューアは、テーマトークンを使わず**白い紙として固定**する。
アプリの面（`--surface`）で描くとアプリの一部に見えてしまい、「病院から送られてきた添付ファイル」に見えない。
メール本文はアプリ内のリーダーなのでテーマに追従してよいが、**添付ファイルの中身は紙**。

参加者が整形する対象が古臭く、整形する道具が新しい。**この対比がそのまま Stage 1 の主題**になり、
「AIを使えばこの古い地獄を片付けられる」を言葉で説明せずに伝えられる。

## 10. 全画面オーバーレイ（開始・罠・罰・解錠の器）

ステージ固有の演出は、すべて**シェルの上に被せるオーバーレイ**として実装する。画面を作り替えない。

| 種類 | 用途 | 見た目 |
| `briefing` | Stage 1〜Finalの開始説明 | 依頼者の顔写真＋メッセージ＋`[了解しました]`。時計は押すまで動かない |
|---|---|---|
| `unlock` | ステージ解錠 | `--ok` の帯が横に走り、次ステージ名が現れる |
| `alarm` | 急変・罠発火 | `--accent` のフラッシュ＋全画面の赤帯 |
| `blackout` | Stage 3 の暗転 | 画面を落とし、白文字1行だけを残す |
| `lock` | 罰ゲーム中 | `--warn` の斜線ハッチでワークスペースを覆い、残り時間を大きく表示。AIチャットは灰色に沈めて入力不可 |

`lock` は Stage 3・4 の罰ゲームで使う。**罰は減点ではなく時間**（企画書§6）なので、
オーバーレイの主役は残り時間の数字であり、叱責の文言ではない。

## 11. 効果音

2026-08-22追加（ユーザー承認済み）。音源は**効果音ラボ**。**音は演出の補助であって、進行の条件ではない**
——鳴らなくてもゲームは同じように進む。音が出ないPCや、音を切った会場でも成立させること。

### 場面と音の対応

| 場面 | 音 | 鳴る位置 |
|---|---|---|
| 急変（赤帯） | `emergency-alert1` | Stage 1→2 の転調、Stage 3・3.5・4 の開始赤帯。帯のスライドインと同時 |
| 院内連絡先の着信 | `mobile-phone-ringtone1` | バッジが光る瞬間。**1回鳴らして止める**——ループさせない（バッジは点いたまま待つので鳴らし続ける必要が無く、会場では他チームの音と混ざる） |
| メール着弾 | `decision1` | Stage 1 の各着弾、Stage 2 の追加分着弾、解錠メールの着弾。**音量は他より小さい**（Stage 1 は6通が立て続けに来るため） |
| 罠発火 | `don-1` | Stage 3 の暗転、Stage 4 の `alarm`。罠の種類は違っても「踏んだ」音は揃える |
| 差し戻し | `cancel` | Stage 2・3・3.5・4・5 の判定NGと、黒塗り罰ゲームの差し戻し。**罠の音とは別の音にする**——差し戻しは失敗ではない（各ステージの「失敗に見せない」扱いと揃える） |
| 解錠・クリア | `success1` | `unlock` オーバーレイの表示時（Stage 2・3・3.5・4）、Stage 1 のクリア結果窓。**Stage 1 の round1・round2 の結果窓では鳴らさない**——差し戻しではなく「ラウンドが終わった」報告であり、事務長の嫌味を読ませたいので音で先に感情を決めない |
| ゴール・感謝状 | `hall-clapping-hands1` | Stage 5 クリアのゴール演出（紙吹雪）と、Final の感謝状。**同じ拍手を共用する**（2026-08-22 ユーザー決定）——レースの終端と研修の終端で同じ「称える音」を鳴らす |

**他チームの解錠でマーカーが動くときは鳴らさない**（§5「通知音は出さない」）。罰ゲーム中も鳴らさない
（Stage 3 の消毒液ボトル補充は「褒めも音も出さず、済んだ本数が増えるだけ」）。

### ミュート

ヘッダー右（時計の左）に🔊/🔇のトグルを常設する。**参加者に見えて構わない**——目的は会場で
ファシリテーターが音を切れることにある。状態は `localStorage` に保存し、同じPCで開き直しても
切ったままにする。切り替えた瞬間に鳴っている音も止める。

> ⚠️ **「効果音を自由に鳴らせるUI」を作らない**（効果音ラボ規約）。ミュートトグルは音を切る
> スイッチであって、音源を選んで試聴させる機能ではない。**サウンドテスト画面を足さないこと。**

### 自動再生制限

ブラウザはユーザー操作を経ていないページの音を止める。**最初のクリック（どこでもよい）までは
鳴らさない**——鳴らそうとして例外を出すのではなく、無音で素通りさせる。Prologue の自動着弾が
最初のクリックより先に走ることがあるため、ここを例外にすると進行が止まる。

## 実装メモ

- トークン名（`--bg` `--surface` `--fg` `--accent` `--rule` `--ok` `--warn` `--ai-surface`）は
  **モックから React 実装へそのまま持ち越す**。モック自体は捨てる前提だが、この命名は資産として残す。
- インジケータの値と `data-mode` は Durable Object のチーム状態に持たせ、再接続・予備機復帰で復元する
  （企画書§9の単一障害点対策）。**転調済みなのに再接続したら平時の色に戻る、は事故**。
- リーダーボードは全体用DOから配信（企画書§7）。自チームの位置はチームDOが持つ。
- 3ペインの固定幅は 1280px 未満で破綻する。会場PCの最小解像度をP0のテストプレイで確認すること。
