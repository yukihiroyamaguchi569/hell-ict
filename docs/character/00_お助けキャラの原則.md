## 狙い

**窓口は一つ。中の人は増えてよい。**

既定の相談相手は情シスの苅部さん一人だが、シナリオの展開しだいで
「これは情シスの職掌ではない」回が出てくる。そのとき**新しいUIを作らずに人を増やせる**ようにしておく。

このファイルは苅部さん個人の設定ではなく、**お助けキャラという機構そのもの**の決まりごと。
ゲストを1人足すたびにここへ戻ってきて、下の不変条件に照らすこと。

---

## 0. 窓口ではない登場人物（相談できない相手は、この原則の対象外）

**「窓口は一つ」が制限しているのは相談相手の数であって、世界に登場する人物の数ではない。**
苅部さん以外が画面に現れる前例は、実は既にいくつもある——いずれも**相談できない形式**なので、
窓口が増えたことにはならず、以下の①〜⑥（ゲストの取り次ぎに課される不変条件）も適用されない。

| 形式 | 例 | なぜ窓口ではないか |
|---|---|---|
| メール（差出人） | Prologueの人事課・前任ICN・夜勤師長、Stage 1の各病棟からの依頼メール | 返信はできるが、対話ではない。往復しても人格として応答しない |
| 全画面の帯・演出 | 急変時の赤帯「5A病棟より緊急連絡…」 | 一方向・一瞬・消える。使い減りする資源として扱う（§1「取り次ぎは使い減りする資源」と同じ思想） |
| 解錠時の一言 | 5A病棟師長「え、もう？ …助かる」 | 報酬演出の一部。会話は発生しない |
| **全画面ブリーフィング** | Stage 1 冒頭の事務長（[苅部さん.md](苅部さん.md) §5、[../scenario/02_Stage1_平常運転.md](../scenario/02_Stage1_平常運転.md) §0） | 一方向で告げるだけ、ボタンは `[了解しました]` の1つのみ。**選択肢が無い＝対話にならない** |

### 判定基準

登場させたい人物が以下のどちらかなら、この原則（§1以降）の対象外——新しいウィンドウ・新しいチャットにさえしなければ自由に出してよい。

1. **参加者が返信・応答できない**（一方向）
2. **1回きりで、常駐しない**（去るのではなく、そもそも留まらない）

逆に、参加者が**やり取りできる**形にした瞬間、それは「窓口」になり、以下の§1〜§3が適用される。

> 📌 事務長のケースでの確認：一方向（①了解しましたのみ）・1回きり（Stage 1冒頭だけ）・
> 正解を知る人物ではない（感染対策の中身には触れない、事務手続きの話のみ）・
> 特定職種を貶めない（丁寧で悪気がなく、本人は褒めているつもり）。
> §2の不変条件①〜⑥のいずれにも抵触しない。

## 1. ゲストは「取り次ぎ」で登場する

新しいウィンドウも新しいチャットも作らない。**苅部さんが電話を回す。**

```
〔苅部〕……それ、私に聞かれても分かりません。
〔苅部〕5A病棟に回します。ちょっと待ってください。

────── 苅部さんが5A病棟へ転送しました ──────

〔みどり〕はい。……で、何を確認したいの?
```

### なぜ取り次ぎにするか

| | |
|---|---|
| **窓口が増えない** | 1画面を3〜4人で囲む前提（[UI 00](../ui/00_共通シェルと通奏低音.md) §1）。窓が2つになった時点で、誰も2つ目を見ない |
| **ログが1本に保たれる** | 相談履歴が積み上がること自体が「同じ人たちと働いている」感覚を作る |
| **取り次ぎ自体が演出になる** | 「専門の人に代わります」＝**手に負えなくなった合図**。無料で緊張が1段上がる |
| **戻れる** | ゲストが去れば苅部さんに戻る。基準点が動かない |

### 取り次ぎは使い減りする資源

赤帯と同じ（[UI 01](../ui/01_Prologue.md) §④）。**毎ステージ誰かに代わると、代わること自体が無意味になる。**
全6ステージのうち**2回まで**を目安とし、使うなら効かせたい回に置く。

## 2. 破ってはいけない不変条件

ゲストを足すときに必ず確認する。**1つでも破ると、窓口を一つに絞った意味が消える。**

### ① 罠ステージ（Stage 3・4）に、正解を知っている人物を出さない

**最重要。** これを破ると設計が振り出しに戻る。

Stage 3 にベテランICNを呼びたくなったら、それは
「正解を知っている人物に**言うなと命じる**」構成に戻ったということ。
ネタバレ防止をプロンプトの我慢に頼る形になり、企画書§7の
「Stage 3 の罠はモデルの気まぐれに依存させない」と矛盾する。

> 罠ステージで欲しいのは**知っている人**ではなく、**在り処を指せる人**。
> 正しさの保証はマニュアルPDFと根拠ページが持つ（[苅部さん.md](苅部さん.md) 狙い）。

### ② 最終セーフティは常に苅部さん

企画書§6「最終セーフティは必ず届き、詰みを防ぐ」。この最後の一段を**ゲストに持たせない**。
ゲストは出ない回もあるし、取り次ぎのタイミングを逃したチームもいる。
**詰み防止だけは、常駐している人物が持つ。**

### ③ ゲストも知識の境界を持つ

deny リスト（禁止語）ではなく、**強い／弱いの2リスト**で定義する（企画書§6 実装欄）。
弱い領域を聞かれたら知らないと言い、在り処を指す。**推測で埋めさせない。**

### ④ ゲストも完成物を作らない

観点と問いだけ。整形済みの表、通知文の全文、会見原稿は出さない。
ソクラテス型・返信遅延・自動で開かない、はゲストにも等しく適用する。

### ⑤ ゲストは去る

ステージが終わったら消え、名前欄は苅部さんに戻る。**常駐させない。**
常駐した時点で「窓口が2つ」と同じことになり、①〜④を守る意味も薄れる。

### ⑥ 特定職種を貶めない

CLAUDE.md のトーンルール。矛先は常に組織と状況へ。
ゲストが苅部さんを見下したり、苅部さんがゲストを悪く言ったりしない。

## 3. UI 側の要件（先に器を用意しておく）

[UI 00](../ui/00_共通シェルと通奏低音.md) §6 の院内連絡先ウィンドウに、以下を織り込んでおく。
**後から足すと会話ログの構造変更になる。**

| 項目 | 決定 |
|---|---|
| 話者の区別 | `〔苅部〕` `〔みどり〕` の前置きだけで区別する |
| **吹き出しの形・色を変えない** | AIチャットとの差が本質であって、人間同士の差は本質ではない。人ごとに色を付けると「キャラUI」になり、企画書§6の別人格・別UIが薄まる |
| 名前欄 | `情シス 苅部` → `5A病棟 みどり師長` に切り替わる。ゲスト中は取り次ぎ元を併記（`（苅部さんが取り次ぎ）`） |
| 取り次ぎの表示 | ログに区切り線＋1行だけ入れる（`── 苅部さんが5A病棟へ転送しました ──`）。演出はここだけ |
| ログの連続 | ステージをまたいでも、話者が替わっても**1本のログ**。クリアしない |
| 遅延・バッジ | ゲストにも同じ。**取り次ぎ直後は特に待たせてよい**（転送された感じが出る） |

## 実装メモ

- **会話ログのレコードに `speaker` を最初から持たせる。** 今は話者が1人しかいないが、
  後から足すとスキーマ変更になる。**今日やっておくべき備えはこれ一つ。**
- システムプロンプトの構造を **話者ごとの人格定義 ＋ 現在の話者 ＋ ステージ文脈 ＋ 知識境界** に一般化する。
  話者が1人でもこの形にしておけば、ゲストは人格定義を1本足すだけで済む。
- 取り次ぎの発火はサーバ（チームDO）が持つ。ステージ進行と滞留時間から決める。
- ゲストを足したら**このファイルの §2 に照らして1件ずつ確認する**。特に①。
- モックは現状 `PHS_LINES` が平テキストの配列で `speaker` を持たない。
  モックは捨てる前提なので追随させない（実装時に上の構造で作る）。
