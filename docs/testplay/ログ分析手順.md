# ログ分析手順

開催後に、D1 `hell-ict-testplay` へ溜まったログをSQLで読むための手順。前作「地獄のAI」Event 91の分析（前作リポジトリ Hell-AI-v2 の `docs/イベント分析/2026-08-28_Event91ログ分析.md`）と同じ観点——ステージ到達時刻、AIの使い方、ボトルネック——を『地獄のICT』でも取れるようにしてある。

## テーブル

| テーブル | 中身 | 書き手 |
|---|---|---|
| `progress_events` | チームの位置（`pos` 0〜7＝Prologue〜Final）と `kind`（`entry` / `clear` / `jump` / `resume` / `reset`） | クライアント（`POST /api/progress`）と、`reset` だけWorker |
| `activity_events` | 発言・提出・判定を1件1行 | Worker（`chat.*` / `thread.create`）とクライアント（`POST /api/teams/:code/activity`） |

`activity_events.created_at` はミリ秒精度のISO 8601（`2026-09-03T02:14:07.482Z`）で、行を書いた瞬間に刻まれる。前作は保存時に一括で書いていたため発言単位の時刻が取れなかった。ここが今回の要点で、会話の間合いや1ステージの滞留時間を後から復元できる。

`event_id` は開催回の識別子。複数回分が同じDBに混ざるので、開催回をまたいで集計するときは必ず絞る。以下のクエリでは `event_id = '02'`（第2回）を例に使う。

値は入室ガードの `EVENT_NO`（開催回2桁）から導出する。**開催前に `wrangler secret put EVENT_NO` で開催回を設定すれば**（`apps/worker` で実行。手順は[開発ハーネス](../development-harness.md)）、`event_id` にも `02` のような2桁がそのまま書かれる。活動ログ専用の変数は持たない——開催回の切り替え忘れが起きる場所を1か所に寄せるため。`EVENT_NO` が未設定のローカル開発とテスト、および値が2桁数字でないときは空文字で記録される。**この変更より前に記録した行の `event_id` は当時の値（`dev` など）のまま残る**ので、古い開催回と混ぜて集計するときは値の形式が違うことに注意する。

コマンドは `apps/worker` で実行する。`--remote` を付けないと本番ではなくローカルのD1を読む。

## 1. チーム別のステージ到達時刻

どのチームがいつ各ステージへ入り、どこで止まったか。前作の「ステージ進行の中央値」に相当する。

```bash
npx wrangler d1 execute hell-ict-testplay --remote --json \
  --command "SELECT team_code, pos, kind, view, MIN(created_at) AS first_at FROM progress_events WHERE kind NOT IN ('jump', 'resume', 'reset') GROUP BY team_code, pos, kind ORDER BY team_code, pos"
```

`reset` はゲームマスターがそのチームを初期状態へ戻した印である（[開発ハーネス](../development-harness.md)）。自力で進んだ位置ではないので `jump` / `resume` と同じく除外する。**リセットを挟んだチームは同じ `pos` を2回通るので、`MIN(created_at)` は1回目の到達時刻になる。** やり直した分を別々に読みたいときは `reset` の `created_at` を境に分ける。`activity_events` 側の対応する行は `gm.reset` で、こちらもリセット前の発言は消えずに残る。

## 2. チーム別のAI発言数と平均長

AIをどれだけ使い、1発言にどれだけ書いたか。`chat.user` が参加者の発言、`chat.assistant` がAIの応答。

```bash
npx wrangler d1 execute hell-ict-testplay --remote --json \
  --command "SELECT team_code, kind, COUNT(*) AS n, ROUND(AVG(LENGTH(text)), 1) AS avg_len, MIN(created_at) AS first_at, MAX(created_at) AS last_at FROM activity_events WHERE event_id = '02' AND kind IN ('chat.user', 'chat.assistant') GROUP BY team_code, kind ORDER BY team_code, kind"
```

## 3. kind別の件数

全体の傾向を1枚で見る。`chat.pii_blocked` や `trap.s3` / `trap.s4` の発火数、`verdict.*` の回数から、罠と判定がどれだけ効いたかが分かる。

```bash
npx wrangler d1 execute hell-ict-testplay --remote --json \
  --command "SELECT kind, COUNT(*) AS n, COUNT(DISTINCT team_code) AS teams FROM activity_events WHERE event_id = '02' GROUP BY kind ORDER BY n DESC"
```

## 4. 1チームの会話を時系列で読む

較正の判断材料は結局これ。`chat.*` だけでなく提出と判定も同じ時間軸に並ぶので、「どんなやり取りの末に何を出して、どう判定されたか」がそのまま読める。

```bash
npx wrangler d1 execute hell-ict-testplay --remote --json \
  --command "SELECT created_at, kind, thread_id, role, view, meta, text FROM activity_events WHERE event_id = '02' AND team_code = '020001' ORDER BY id"
```

`thread_id` で束ねるとステージごとの文脈が追える（画面はステージごとに会話が切り替わるので、`thread_id` はおおむねステージに対応する）。

## 読むときの注意

- **PIIは保存していない。`text` と `meta` は独立に落とされる。** 保存直前に両方を検査し、`text` にPIIがあれば `text` だけを空にし、`meta` にPIIがあれば `meta` だけを `{"piiRedacted": true}` へ丸ごと置き換える。片方が反応してももう片方は残るので、「`text` が空なら必ず `meta` も消えている」わけではない。送信前ゲートで止まったチャットは `chat.pii_blocked` として残り、本文は最初から保存されない。いずれの場合も「いつ何が起きたか」の時系列は残る。
- **同じ `command_id` の再送は行を増やさない。** `(event_id, team_code, command_id, kind)` のUNIQUEとINSERT OR IGNOREで潰しているので、件数はそのまま実際の発言数として数えてよい。`command_id` はクライアント採番のため、キーに `event_id` と `team_code` を含めて別チーム・別開催回の衝突を避けている。
- **ログの欠落はありうる。** サーバ側の記録は `waitUntil` で非同期に書き、失敗しても握り潰す（記録のためにゲームを止めない設計）。件数の突き合わせが合わない場合はまずこれを疑う。
- **2026-09-06 以前の `view` と `kind` は旧番号で入っている。** 画面の内部名を表示番号へ揃えたのはこの日で（Issue #118）、それより前に積んだ行はD1に旧名のまま残してある（過去のログは書き換えない方針）。読むときは次の対応で読み替える。

  | 旧名（2026-09-06 以前） | 新名 | 参加者に見える名 |
  |---|---|---|
  | `s35` / `submit.s35` / `verdict.s35` | `s4` / `submit.s4` / `verdict.s4` | Stage 4 新情報の解釈 |
  | `s4` / `submit.s4` / `verdict.s4` / `trap.s4` | `s5` / `submit.s5` / `verdict.s5` / `trap.s5` | Stage 5 報告 |
  | `s5` / `submit.s5-prompt` / `select.s5` | `s6` / `submit.s6-prompt` / `select.s6` | Stage 6 掲示 |

  切り替えの境目は**デプロイ時刻（PRのマージ時刻）**で区切る。デプロイ後も開いたままの旧タブは旧UIのまま動き続けるので、切り替え直後の数分は旧 `kind` が混ざりうる——`view` はサーバが入口で新名へ直すが（`s35` のみ。`s4`・`s5` は判別できない）、`kind` は値だけでは新旧を判別できないため読み替えていない。境目付近の行は `created_at` を見て、どちらのUIから来たかを判断する。

  `s1`〜`s3`、`final`、`entry`/`welcome`/`inbox` は不変。`s35` は新体系に存在しないので見つかれば必ず旧番号だが、`s4`・`s5` は新旧どちらの体系にもある——開催回（`event_id`）と `created_at` で、どちらの番号体系で書かれた行かを判断する。2026-08-23（`event_id = '02'`）のログは全て旧番号である。
