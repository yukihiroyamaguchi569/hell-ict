# 2026-09-09 ゲーム体験改善提案

## 目的と前提

9月はモックで本番を行う。3〜4人が1台のPCを囲む集合研修として、ゲーム中の協働、AIの判断、達成感を高めるための提案を残す。これは実装決定ではなく、今後のモック改善と当日運営を検討するための案である。

UI改修フェーズでは `docs/ui/mock/index.html` が正典である。ただし今回はモック自体を変更しないため、モック以外の正典との整合確認や改訂も行わない。

## ゲーム体験の改善案

### 2. 全員に「自分が突破に貢献した場面」を作る

既存のブリーフィングにある「打つ」「読む」「決める」という役割を手がかりにしつつ、役割は固定しない。ステージが変わるたびに、操作する人を交代してもよいことをゲーム中の中立的な表示で後押しする。

固定役職にすると、役割を守ることが目的になり、チームがその場で必要な動きを選びにくくなる。特にStage 3の復旧後には、操作していなかったメンバーにも、何を根拠に判断を変えたかを話せる場をつくる。全員が突破への貢献を実感できる状態を目指す。

### 3. Stage 3は立て直した瞬間を大きく扱う

正典を照合して復旧できた直後に、現場からの返答と短い余韻を置く。たとえば、差し替えた通知が現場で使われ始めたことを示し、チームが自分たちの判断を確かめられるようにする。

振り返りでは、どの情報を基に判断を変えたかを聞く。罠にかかったことだけで終わらせず、AIの出力を鵜呑みにせず立て直せたことを成功として残す。

ただし、罠の前に検証方法や復旧経路を予告しない。復旧はアプリ内マニュアルを自力で照合する経路に限る。

### 4. ステージごとに病院が少し助かったことを返す

各ステージをクリアしたとき、既存の中央ペインに1〜2行の現場反応を返す。大きな新演出やポップアップを増やすのではなく、作業の成果が病院に届いたと分かる短い応答にする。

たとえば、次のような反応である。

- 「夜勤への引き継ぎに、この一覧を使えます」
- 「病棟からの確認電話が落ち着きました」
- 「受付と病棟入口への掲示が完了しました」

ゲームの進行ごとに、チームの仕事が現場を少しずつ助けている実感を積み上げる。

### 5. 感謝状をこのチームだから贈られたものにする

既存Finalの成果物タイル、労い、感謝状を生かす。9月はファシリテーターが各班の良い判断を一つ拾い、紹介することから試せる。

将来は、PIIを含まない活動ログから、班ごとの成果物や判断を感謝状へ自動反映することも候補になる。これは9月のスコープを増やす決定ではなく、感謝状を具体的な達成の証拠で支えるための将来案である。

### 6. 最後の5分でゲームを自分の仕事につなげる

ゲームの最後に、各自が翌日にAIを試す具体的な業務を考える時間を置く。「議事録」だけで終えず、どの会議の、誰に渡すものかまで具体化する。

持ち帰り資料には、依頼の組み立て方と、出力を確認するときの問いを載せる。これはデブリーフィングの「少し先の未来」と相互に補強する運営提案であり、既存の進行台本は変更しない。

## 9月に試す順序

まず、2の操作交代を促す中立表示、3のStage 3復旧後の短い余韻、4のクリア時の現場反応を、ゲーム中の小さな改善として試す。

5の班ごとの良い判断の紹介と、6の翌日に試す業務の具体化は、当日の運営で試す。

## 実装時の境界と確認

Stage 3の罠とアプリ内マニュアルによる復旧、Stage 5のPIIをOpenAIへ送る前に止めるゲートは不変条件として維持する。罰は減点ではなく時間で払い、AIチャットは現在のステージの会話だけを表示する。

3〜4人でのリハーサルでは、全員が会話と判断へ参加できたか、Stage 3でどの根拠から復旧できたか、完走までの時間、迷った場面を観察する。
